# 路线图与进度 / Roadmap & Progress

目标：把 Cairn 从"能用但早"的基础推进到工业级引擎（对标 Unity）的能力。这份文件是
**唯一的进度账本**：路线图、每个增量的范围、以及"下一步做什么"都以它为准，CHANGELOG
负责记录每次改动的细节。

## 工作原则

1. **每个增量都具体可行。** 一次提交解决一个能说清楚的问题，范围小到可以完整验证。
2. **版本号跟着层走。** 0.1.x 是 0.1 层（基础与正确性）的增量；2D 管线这一层（0.2）收口时
   公开版本号进入 `0.2.0`，此后的增量按 `0.2.x` 递增。每次增量是一个本地提交 + 一个注解 tag，
   先不推送。
3. **正确性由软件路径定义。** 软件光栅化器是参考实现，测试套件固定跑它。GPU 路径的
   存在意义是加速，不是引入第二套语义——两条路径之间任何画面差异都算 GPU 侧的 bug。
4. **改渲染必须两条路径都验。** 见文末"验证方法"。

| 0.1.28 | 渲染质量：命名剪辑（一张图上的多段动画） | 一个动画器只有一段动画：角色有 idle / walk / attack，就只能堆组件、每次切换手工搬 `firstFrame`/`lastFrame`/`fps`/`loop`，而帧区间只是两个整数，没有名字可存、可读、可写。现在 `clips` 是一张表（每项 `name` + 可选的 `columns`/`rows`/`firstFrame`/`lastFrame`/`fps`/`loop`），`clip` 指定正在播的那条；缺失的键回落到组件自己的字段，所以一条剪辑是"覆盖"而不是"复制"，没有表的动画器行为与 0.1.27 完全一致。表用新的反射种类 `EditorPropKind::Json` 承载（引擎不解释、原样存取），因此场景文件、`component.setProps`/`get`、检视面板都能整表进出；`DrawnCell` 让切换在"被画出的那一帧"生效（未走过 tick 时是新剪辑的第一格），下一次 tick 才真正重启（帧与帧计时归零）。`TestSpriteClips` 两条后端反向验证；CLI 346 → 372 项 |
| 0.1.29 | 渲染质量：动画参数与过渡（状态机） | 命名剪辑是数据不是行为：什么时候切哪段动画全靠脚本每 tick 改写 `clip`，“走 → 攻击 → 回待机”的时序落在组件之外，场景文件、批处理与测试都看不见。现在 `params` 是动画器读取的值（`{"moving":true,"speed":2.5,"attack":false}`），`transitions` 是按顺序求值的转移表（`{"from","to","when","waitForExit"}`）：`from` 为 `"*"`（也是默认值）表示任意状态，`when` 是一条条件或“必须全部成立”的条件列表（`is`/`not` 按布尔、`gt`/`lt` 按数值、`trigger` 是一次性事件），`waitForExit` 等当前剪辑播完一整遍（格数 / fps）才切。第一条命中即生效，所以表序就是优先级，整台机器是“状态 + 参数 + 已播时长”的确定性函数；`EvaluateTransitions` 会清掉被它消耗的 `trigger`（`params.attack` 随后读回 `false`），自转移（`from`/`to` 同名）则是重播该状态。每个 tick 先 `AdvanceAnimation` 再求值，因此退出时间看到的是刚播完的那段剪辑，进入的状态就是这一帧画出来的第一格。`TestSpriteTransitions` 两条后端反向验证；CLI 372 → 403 项 |
| 0.1.30 | 渲染质量：逐帧时长（一条剪辑内部变速） | 一个 `fps` 是整段动画一个速率，说不出“蓄力慢、出招快”：要么匀速播，要么拆成多条剪辑、切换时机靠手写。`durations` 是每个格子自己的秒数（组件上的字段，也是剪辑条目上的键），下标从该剪辑自己的 `firstFrame` 数起，所以一张表描述的就是它自己的格子顺序；表里没提到的格子（或给了 0、负数、非数字的）用剪辑自己的 `1 / fps`，于是空表与只看 `fps` 完全等价（0.1.27–0.1.29 的行为逐位不变）。条目自己的表覆盖组件字段，`[]` 则清空组件表、按速率播。`CellSeconds` 一处定义“这一格显示多久”，`LengthOf` 把它按格子加起来，因此退出时间（0.1.29 的 `ClipLength`）量的是剪辑自己的长度而不是 格数 / fps——慢蓄力在两个地方都慢。步进循环从“能塞下几个整步”改成“一次走一格”（要减的时间取决于当前是哪一格），护栏不变（超过一整遍的停顿仍夹到一遍）。`TestSpriteFrameDurations` 两条后端反向验证；CLI 403 → 416 项 |

## 阶段：场景与预制体（0.1）

**已做（0.1.17）**

- **实例记录差异，其余交给资产。** `PrefabInstance::overrides` 保存"这个实例相对 `.prefab`
  改了哪些属性"，与场景一起存盘。加载场景时先把资产回填进实例，再把记录覆盖回去——于是
  "改资产"能到达所有**没改过该属性**的实例，"改一个实例"也不会被回填冲掉。这就是 Unity
  的模型，也是本文件此前排在最前的场景级缺口（0.1.3 的模板 + 链接没有记忆，改实例要么
  全局生效、要么在回填时丢失）。
- **记录是"两棵序列化子树的 diff"**，在存盘、`prefab.overrides` 与 `prefab.apply` 时现算，
  而不是靠拦截属性 setter。所以经由**任何**路径造成的改动都算数：CLI 设的属性、物理写回
  的 `Transform`、脚本属性、编辑器里关掉的组件——拦截 setter 会漏掉这几类。
- **键是可读的路径。** 节点路径（`""` 根、`"Lid"` 子节点、`"Body/Wheel"` 更深）+ 属性键：
  `@name` / `@active` / `@tag` / `@layer`、`MeshRenderer.albedoColor`、
  `MeshRenderer.@enabled`、`Transform.position`、`Script.speed`，以及
  `@removedChildren` / `@removedComponents`（实例删掉的节点/组件）。节点按"同名同级、按
  出现顺序"配对，重复名字也能对上。
- **数值比较带容差，这一条是必需项。** JSON 写出只用 10 位有效数字（`%.10g`），回读出来
  的 `double` 与原值不等；精确比较会在**第一次重新加载**时把资产里每个 float 都判成
  "改过"。相对 1e-6（0 附近绝对 1e-9）比写出误差高四个数量级、比人工改动的粒度低三个
  数量级，正好分开"文件被读回来"和"这个值被改过"。
- **删除要记住才是删除。** 在某个实例上删掉的组件/子节点记进 `@removed*`，之后的 sync
  不会把它加回来（否则每次加载都会撤销你的删除）；资产自己仍有那个节点，记录只对**这一个
  实例**抑制它。
- **旧场景不丢工作。** 0.1.17 之前存的场景没有记录（`overridesKnown = false`），加载器就
  把实例自身的状态当作记录（先算 diff）而不是让资产覆盖它；`prefab.instantiate` 出来的
  新副本则相反——它**就是**资产，记录为空且标记已知。
- **命令。** `prefab.overrides --id`（刷新并逐属性列出差异）、`prefab.sync [--id]`（回填
  资产，省略 `--id` 即全部实例——就是加载场景时自动做的那件事）、`prefab.apply`（记录差异
  → 回填资产但保留差异 → 把实例写回成新资产，同级实例立刻跟上）。

**下一步候选**

1. **节点身份。** 现在按"名字路径"配对节点，所以重命名/换父会让该节点脱离模板（旧名字被
   记为"移除"，节点本身作为实例新增保留，之后不再跟随资产）。Unity 用资产内 fileID +
   实例内映射解决，是这块的地基。
2. **嵌套预制体与变体。** 预制体里的子树自己也是实例；以及"基于某预制体派生的变体"。
3. **结构增删的对等传播。** 资产删掉的节点目前不会从别的实例上消失（`@removed*` 只抑制
   实例自己的删除），要靠 `prefab.revert` 收敛。

**已做（0.1.34）**

- **构建这一步只在人想起它的时候发生。** `Script` 组件在游戏开始时按名字解析自己的类，而类只存在于
  "注册它的库被加载进进程"之后；编辑器此前只有一条路能做到这件事——显式点 **Build Scripts**。于是
  新建的 `project-2d` 打开、按播放、控制台给出引擎的原话 `script class not found: Player2D (build
  scripts first)`：玩家站在原地不动，而这句话说的是引擎的状态，不是"按哪个按钮能修"。修复前已确认
  这不是脚本的问题（手工编译并加载后，按住方向键 x 从 -5 走到 1.775），而是缺了一段生命周期。
- **陈旧是一个纯函数。** `scriptStatus`（`editor/main/build.js`）把 `Library/GameScripts.<ext>` 与
  `Assets/Scripts` 下的所有文件比时间戳，给出四态：`nosources`（没有可编译的源）、`missing`（有源无库）、
  `stale`（有输入比库新）、`current`。输入包含**头文件**：没有依赖扫描器，时间戳判断无法知道哪个头文件
  会被哪些翻译单元包含，所以"比库新的那个文件赢"，不理会它是否真的被包含。它同时返回据以判断的
  `output` / `outputMtime` / `newestInput` / `newestInputMtime` / `sources` / `headers` / `bytes`，
  所以 `script.status` 报的是理由而不是结论。
- **"已经是最新"可以被要求成一次空操作。** `buildScripts(dir, compiler, {ifStale:true})` 在 `current`
  时直接 `{ok:true, skipped:true, output, durationMs:0}`：命令仍然给出一个可加载的库，但不拉编译器
  （也因此，没有装编译器的机器只要无事可做就不会报错）。其余路径——`noSources`、真正的编译、编译器诊断、
  启动失败——与从前一模一样。
- **编辑器的三条入口现在共用它。** 打开工程跑 `syncScripts()`：`current` 只加载、`missing`/`stale`
  先编译再加载、`nosources` 什么都不做；**Ctrl+B** 与保存 `.cpp` 只在真有改动时编译，**Rebuild Scripts**
  始终调编译器——自动路径不再为一次"编译不出不同结果"的编译付费，而有意为之的那条路径依然可以。
- **场景需要而进程没有的类，在开播前就有名字。** 按播放时把每个 `Script` 组件的 `class` 与已加载集合
  比对，缺失的类名同时写到状态栏与控制台面板，于是这条信息出现在按下按钮的那一刻，而不是一秒后埋进
  运行日志里。
- **验证。** CLI 496 → 517 项（新增 `cli: script staleness (script.status + script.build --ifStale)` 段）：
  刚建好的库是 `current` 且其上的构建是空操作（但仍报出可加载的类）；把库的时间戳改旧即为 `stale`；
  随后写入的头文件自己成为 `newestInput`；`stale` 会被真正编译并回到 `current`；删掉库是 `missing`
  且 `--ifStale` 会建它；`Assets/Scripts` 为空的工程是 `nosources` 且 `script.build` 以 `not_found`
  拒绝。反向验证五处：`collectHeaders` 不收集头文件 → 1 项失败；忽略 `current` 判断（永远跳过）→ 12 项失败；
  永不跳过 → 1 项失败；时间戳比较反了 → 5 项失败；把缺库报成 `current` → 11 项失败。编辑器自己那条路
  走的是同两个调用，用真编辑器手工走过：新建 `project-2d` 打开后第一次播放角色就能动，没有先按任何按钮。
- **仍开着。** 陈旧是时间戳而不是依赖：碰一个没有任何翻译单元包含的文件仍会触发编译，而别的工具用不同
  源编出来的库只要时间戳更新就照样算 `current`。库里的 `engine.version` 仍是编译期常量，所以上一版引擎
  编出的库会先是 `current`、加载时才被拒。编辑器没有 UI 测试框架，因此控制台那行与状态栏文案只有上面
  那次手工验证。

## 阶段：渲染质量与 2D 管线（0.2）

**目标。** 让"画出来的东西"在画面里就是对的样子：形状不丢、像素不糊、上下不反。
软件光栅器是参考实现，所以这条线的每个修复都先落在软件路径，再用跨后端测试盯住 GPU。

**为什么是它。** 项目的核心是"AI 自己画素材做游戏"，但 2D 这条路此前几乎无人走：
`templates/project-2d` 一直在用 `SpriteRenderer` 和 `TextRenderer`，可没有任何测试渲染过它，
手写的文档里也一个字都没提过这两个组件（只在自动生成的 `docs/cli.md` 命令表里出现），
`test/smoke.js` 里没有精灵用例——于是 2D 攒下了一串**结构性**的错，连模板里那行标题文字
上下整个反了都没人发现。

**已做（0.1.22）**

- **每个 2D 四边形只画了一半。** 共享的 2D 顶点缓冲是"三角形列表"布局（`AppendQuad`
  每次压 6 个顶点：`{0,1,2,0,2,3}`），GPU 侧原样上传 6 个顶点、按三角形列表画，是对的；
  软件侧的 `EmitQuadVerts` 却把前 4 个顶点当成四角、再自己拆 `{0,1,2},{0,2,3}`——第 4 个
  顶点其实是 `w0`，于是第二个三角形退化成一条线被丢掉。表现是**每个精灵、每个字形都少了
  一个三角形**（固体色贴图在一块满屏四边形上只剩一个三角）。修法：按三元组切分共享的
  顶点块，两个后端于是看到同一份三角形列表。
- **像素完美精灵在 GPU 上被线性 + mipmap 采样。** `pixelPerfect` 在软件路径是最近邻
  （且强制 lod 0），在 GPU 路径却映射到 `linearClamp`——而 `linearClamp` 是用
  `VK_FILTER_LINEAR` 建的（唯一的最近邻采样器 `nearestClamp` 只给阴影用）。于是
  AI 画的像素画在默认 GPU 后端被糊掉，且两条路径画面不一致（违反工作原则 3）。修法：
  新增 `pixelClamp`（`VK_FILTER_NEAREST` + clamp + `maxLod 0`，mip 链永远不会被选中），
  `pixelPerfect` 的 albedo 与法线图都改用它。
- **验证定的是像素。** `engine/tests/engine_test.cpp` 的 `TestSpriteQuality` 用一张
  16×16 红/蓝逐像素棋盘，在 128×128 视口里让精灵盖满（`pixelsPerUnit` 6、`orthoSize` 2）：
  四个象限中心都必须非背景色（漏三角形会露黑），精灵内部只允许出现**两种**颜色
  （线性采样会混出紫）。`test/cli.js` 新增 "sprite 2D rendering quality" 段（+11 项），
  用 `image.*` 现画一张四象限精灵 → `SpriteRenderer` → `render.screenshot` →
  `image.pixel`/`image.palette --list`：整帧恰好 4 色、且不含背景黑。

**已做（0.1.23）**

- **精灵和文字上下反了。** 图像空间在引擎里处处是"y 向下"：`image.draw.rect` 的 y=0 是上边、
  PNG 第 0 行是上边、贴图的 `v=0` 是第 0 行。但 2D 四边形的角点顺序是
  `{左下, 右下, 右上, 左上}`，两个调用点都把 `v=0` 配给了**下**面的两个角，于是贴图的上边
  画到了世界下方：每个精灵、每个字形都上下镜像（`flipY` 只翻几何，不理顺贴图 v 的关系）。
  修法：精灵的 uv 改成 `{{0,1},{1,1},{1,0},{0,0}}`，字形 quad 的两个下角取
  `g.v + g.h`——**图的上边 = 世界的上边**。
- **顺带把绿通道的约定定了（这是修朝向必须一起回答的问题）。** `image.normalMap` 把法线
  按图像空间编码（`ny = -dh/d(图像 y)`，即 G<0.5 表示法线朝**图像上方**倾斜）。朝向修好
  之后"图像上方"就是"世界上方"，于是 `sprite.frag` 与软件路径里那句 `-(绿通道)` 正好是
  对的——它此前和镜像的 albedo 恰好配成一对，所以翻转 v 反而让光照与贴图重新对齐，而不是
  需要额外改绿通道。这个约定被钉成了测试：`TestSpriteNormalOrientation` 用两张只差绿通道的
  法线图（朝图像上 / 朝图像下）配一盏正上方的点光，断言朝上那张亮——软件与 GPU 两份重映射
  各测一次。
- **验证。** `TestSpriteOrientation`（16×16 上红下蓝的精灵 + 大写 `T`：上排是满横杠、下面
  是一像素竖笔画）在软件与 GPU 两条路径上分别断言"红在画面顶部"和"字形墨迹的上几行远比下
  几行密"；`test/cli.js` 的精灵段加了 4 项朝向断言（红/蓝在上、白/绿在下），另加一整段
  "2D orientation (up is up)"（+7 项）用 `TextRenderer` 渲染 `T` 并逐点读回。反向验证：
  把两处 uv 改回旧写法 → 引擎 6 项失败（两条路径 × 精灵/文字）、CLI 6 项失败；把两条路径的
  绿通道正负号各改一次 → 引擎 2 项失败。
- **顺带修好了模板。** `templates/project-2d` 的标题 "ARROWS / WASD TO MOVE - SPACE TO JUMP"
  此前在场景里是上下反的；现在渲染出来是可读的、正的（把标题从 `render.screenshot` 里
  `image.crop` 出来、再用 `image.preview --format blocks` 打印，首个字形 `A` 的尖端在上）。

**已做（0.1.25）**

- **每个精灵只能整张画。** `SpriteRenderer` 没有子矩形，"一图多帧"写不出来——`image.stamp`
  早就能拼图集，但精灵这遍把整张贴图按写死的 uv（`{{0,1},{1,1},{1,0},{0,0}}`）一次画完，
  而且世界尺寸恒等于"整张贴图 / pixelsPerUnit"，一张 4 帧的横条会被拉成一整条。
- **`uvRect` 是归一化图像坐标下的 `{x, y, w, h}`。** `(x, y)` 是矩形左上角，所以默认
  `{0,0,1,1}` 就是整张；`cols`×`rows` 图集的第 `(col, row)` 帧是
  `{col/cols, row/rows, 1/cols, 1/rows}`。行从上往下数，与 `image.stamp` 拼帧的顺序、以及
  引擎里其他所有图像坐标一致（0.1.23 已定"图的上边 = 世界的上边"）。绘制尺寸随矩形
  （`帧像素 / pixelsPerUnit`），uv 就是矩形的四个角——0.1.23 的修法被自然推广：两个**上**角
  仍然取矩形的低 v，所以图集不可能悄悄把镜像问题带回来。
- **`pivot` 是精灵自身坐标里的点。** 落在实体位置上的那个点，坐标系与 `uvRect` 相同：
  `(0,0)` 左上、`(1,1)` 右下；默认 `(0.5, 0.5)` 与旧行为逐像素一致（已有场景一个像素都不动），
  `(0.5, 1)` 让帧"站在"原点上。`flipX` / `flipY` 现在绕 **pivot** 镜像而不是绕中心，于是翻转
  一个有脚的角色能保持脚不离地。两个字段都进了 `SpriteRendererDefs`：场景 JSON、
  `component.add` / `component.setProps`、`component.schema` 与编辑器检查器都自动支持。
- **验证。** `TestSpriteAtlas`（新）：一张 16×16 四象限 BMP（由新的 `WriteTestBmpSheet` 按
  阅读顺序写盘）在两条后端上各跑一遍，逐个 uvRect 断言"点到的那一帧就是画出来的那一帧"
  （四个象限四种颜色，忽略 uvRect 会画出另一种），并断言绘制尺寸是**帧**的（按整张算会让
  本该是背景的四角被盖住）；再让 `pivot = (0, 1)` 的精灵必须只占视口的右上象限——pivot 的
  两个轴、两个方向都被钉住。这个场景把环境光设成白、tonemap 关掉，贴图上的颜色原样落进画面，
  于是断言可以精确比色而不是"不是黑"。CLI 侧新增 `cli: sprite atlas (uv rect + pivot)` 段
  （+18 项，298 → 316）：用四次 `image.draw.rect` 画一张 32×32 图集，按 `pixelsPerUnit 16`
  只画指定的一帧，再用 `image.pixel` 读回那一帧与四周背景；再把四个 uvRect 各挂一个精灵、
  统一 `pivot = (0, 1)` 拼满视口，逐个象限读色。
- **反向验证（两处）。** 把 uv 矩形（连带尺寸）写死成整张 → 引擎 16 项失败（两条路径 ×
  四种矩形 × 尺寸断言）、CLI 3 项失败；把 pivot 写死成中心 → 引擎 4 项失败、CLI 3 项失败。
  两次都改完、编译、确认失败、再还原（先把 pivot 那次还原并重编，再试 uvRect，以便归属清楚）。

**已做（0.1.26）**

- **2D 剔除量的是一个跟精灵无关的数。** `float w = sp->pixelsPerUnit * 0.5f` 并关于原点对称：
  它只跟 pixelsPerUnit 有关，看不见贴图、看不见 uvRect、也看不见 pivot。两个方向都错——
  实体在视野外、像素却盖住整个视野的精灵（`pixelsPerUnit` 小于 1，背景/视差层就是这么设的）
  被整个剔掉，屏幕上什么都没有；而默认 100 px/unit 的真正离屏精灵被算成 50 单位的巨物，
  每帧都提交再被裁掉，而不是提前丢弃。
- **边界现在就是那片四边形，且只有一处定义。** `SpriteLocalExtent`（renderer.cpp）由一个
  `SpriteRenderer` 加贴图像素尺寸算出四边形在局部空间的展开（`uvRect` 的像素 / pixelsPerUnit，
  按 pivot 偏移，`flipX`/`flipY` 取反），视锥测试与顶点生成都调它，两者不可能再各说各话。
  贴图在 gather 阶段解析一次，同一个 `shared_ptr` 交给绘制：定边界的尺寸就是建四边形的尺寸。

  `clip`，时序——也就是动画本身——落在组件之外，场景文件、批处理与测试都看不见。播放模式早就

- **`params` 是动画器读取的值。** 一个结构化对象（如
  `{"moving": true, "speed": 2.5, "attack": false}`），由脚本或 `component.setProps` 写入，

  所以布尔被当数字比较时读成 0/1 而不是报错——与剪辑表"缺失的键回落"是同一套宽容规则。
- **`transitions` 是按顺序求值的转移表。** 每项 `{"from", "to", "when", "waitForExit"}`：
  `from` 是它适用的状态或 `"*"`（也是默认值，所以 `{"to": "attack", "when": [...]}` 表示"从任何
  状态"），`to` 指定要进入的剪辑，`when` 是一条条件或"必须全部成立"的条件列表，`waitForExit`
  让转移等到当前剪辑播完一整遍。第一条命中的条目生效，于是表序就是优先级，整台机器是
  （状态、参数、已播时长）的确定性函数——同一串参数与 tick 必然重放出同一串帧，因此批处理
  能渲染某个状态的某一帧。
- **条件是 `{"param", "op", "value"}`。** `is` / `not` 按布尔比较（裸 `is` 就是"为真"，不需要
  `value`），`gt` / `lt` 按数值比较，`trigger` 是一次性事件。动画器没有的参数"什么都不成立"
  （在它上面是惰性的，而不是被当成 false），不存在的 `op` 永不命中，因此手写或改了一半的表
  会退化成惰性，而不是乱切状态。
- **`trigger` 被触发它的那条转移消耗。** `EvaluateTransitions` 清掉命中条目里的每个 `trigger`

**已做（0.1.31）**

- **动画中途说不出话。** 蓄力与出招是同一条剪辑，中间有一下：窗口打开、判定该生效、这一脚已经落地——

- **`events` 是剪辑上的一张表**：`[{"at", "set"}]`，进入 `at` 指的那一格时把 `set` 写进参数。`at` 从
  剪辑自己的第一格数起（`{"at": 1}` 就是它自己的第二格，与区间放在哪里无关），`-1` 是最后一格、
  越界按帧的规则夹住；`set` 就是 `transitions` 读的那只袋子，于是剪辑能打开它自己状态机等待的那个窗口，
  值也原样写入——真值、数字、字符串都行。这个键在组件上与在剪辑条目上都有，规则与 `durations` 相同：
  条目自己的表覆盖组件字段，`[]` 清空组件表。
- **进入格子是唯一的触发条件。** 剪辑第一格在"进入剪辑"时触发——开播、手写 `clip`、转移进入状态，
  因为 `Restart()` 就是这个引擎里"进入"的定义；之后每步进一格触发一次（引擎的步进一次只走一格），
  所以一个很长的 `dt` 会按表序依次触发它经过的每一格，一 tick 内最后一次写入的就是参数里剩下的值。
  循环剪辑每一遍都会再触发。全程不看墙上时钟，因此同一串 tick 写出的值与顺序完全一致；没有 `at`、
  没有 `set`、`at` 不是数字的条目一律跳过，不去猜。
- **读事件就是读参数。** 没有队列要排空、没有回调要接线：脚本里 `anim->Param("landed")`、CLI 里
  `component.get`，触发过的痕迹只有它写下的值。`trigger` 由触发它的那条转移消耗，而被进入状态的事件
  先跑——于是"事件又写了刚被消耗的那个 trigger"会跟着一起被消耗，而不是每 tick 重新武装机器。
  这个次序本身也进了测试，因为反过来写就是一张不用输入也能每 tick 走一个状态的表。

**已做（0.2.1）**

- **阴影画进了深度图，却没画进画面。** `shadow.vert` 在光栅化级联前把裁剪空间 y 取反，于是深度图
  按自上而下的行写入，行号是 `(1 - (ndc.y * 0.5 + 0.5)) * size`——软件阴影图也是这个朝向。`mesh.frag`
  的 `sampleShadow` 却读 `(ndc.y * 0.5 + 0.5) * size`，也就是这张图的镜像行，取到的永远是空深度，
  比较恒过、没有一处表面被压暗。软件路径照常画出阴影，`TestShadows` 又只在软件上跑，没有用例比过
  两张掩码，于是整个功能失效而套件全绿。同一个 400x300 的 `project-3d` 游戏帧与软件参考相差 >2 级
  的像素是 2983；把行翻回来后 GPU 把阴影落在同一片像素上（320x240、级联 1/2/4 × 距离 30/60：
  软件 841–1065 个阴影像素，GPU 828–978，质心相差不到 1 px）。
- **网格的每条共享内边都有一条一像素暗线。** `RasterTriangle` 丢掉一切圆心落在三角形外的像素，
  跨在共享边上的那个像素于是既不属于左三角形也不属于右三角形，留下的是背景。新建 3D 工程的
  Ground 平面正是两个三角形加一条对角线，暗线横穿整个面，那一帧有 311 个这样的像素。现在先算
  覆盖率：圆心落在某条边外半像素以内的像素也归这个三角形，因为那半个像素确实被它盖住；
  `antialias == false` 仍走严格的圆心判定，硬边路径不受影响。
- **半覆盖像素被反复混合。** 同一表面上两个三角形都会认领边上的像素，各自按 src-over 混一次，
  就各自把对方没盖住的那部分背景叠了一遍，越叠越暗。现在半覆盖的不透明像素在清屏时抓下的
  只含天空的底图（`aaBackground`）上补自己的那一份，权重是
  `share = min(coverage, 1 - aaCover[pix])`，`aaCover` 累加已覆盖面积——三个三角形共角也填不两遍；
  完全覆盖的像素仍走 src-over。那一帧的暗缝像素 311 → 0，与 GPU 相差 >2 级的像素 1661 → 866。
- **精灵的对角线有同一个毛病，而且更明显。** `mat.blend` 的项按三角形合成：一个精灵四边形的两个
  三角形各自混合自己那一半被边切开的对角像素，背景于是被算了两遍，精灵中间多出一条淡暗线。
  任何开着边缘覆盖的精灵（也就是所有非 `pixelPerfect` 的精灵）都有。2D 通道现在把材质标成
  `item2D`，并按刚发射的三角形范围清掉上一项留下的覆盖（`ClearItemCoverage`），所以一个四边形的
  两个三角形只填一次像素：每个加上自己那一份四边形颜色，叠在该项下面的颜色（`aaBlendBg`）上，
  后者在第一个三角形碰到该像素时抓下。黑底上旋转 30° 的白精灵，中间行原来在 196 的四边形里
  有 172，现在整行 196。
- **测试比的是图，不是统计数字。** `TestShadowsAcrossBackends` 在同一场景上分别开/关阴影、两条
  后端各出一帧，把变化了的像素当作阴影区域：软件侧数量 >200 且质心在投影物下方，GPU 侧面积相差
  <25%、质心相差 <3 px——镜像行会同时让三条失败。`TestInteriorEdgeAntialiasing` 用正对着的
  unlit 平面填满 160x120：每个像素都必须等于表面本色，不允许更暗或更亮，两半修复各自被它抓住。
  `TestSpriteEdgeAntialiasing` 在黑底上画旋转精灵，要求共享对角线经过的中间行整行同色，同时轮廓
  外侧仍保留中间值——强制关掉按四边形合成就会红。`TestCullingAndAA` 的四边形从 6 缩到 2.5 单位，
  让它数的抗锯齿像素是轮廓而不是已经不存在的接缝。CLI 没有命令变化，529 项不变。
- **三次变异各自被抓住。** 把 `fy` 翻回去：三项 GPU 阴影检查失败；恢复只认圆心的归属判定：
  `darker == 0` 与 `TestCullingAndAA` 的剔除计数失败；强制 `perQuad` 为假：`seam == 0` 失败。
  每次都是改代码、构建、看到失败、还原；套件另外在 `VK_LAYER_KHRONOS_validation` 下跑过，报告干净。
- **仍开着。** 同一个 3D 游戏帧上两条后端还剩 862/120000 个像素不同，剩下的是轮廓边缘的半像素
  约定（GPU 的采样点落在软件判定为「外」的那一侧），不是几何也不是阴影；点光源与聚光各让一张
  320x240 的帧有约 0.5% 的像素相差 >2 级，后处理链（bloom、暗角、对比度、饱和度）约 0.8%、
  平均不到 1 级。`RenderStats.shadowedPixels` 仍只由软件路径计算，GPU 帧即便开着阴影也报 0；
  新用例比的是图而不是这个数，这个统计值需要一条 GPU 侧的计数。

**下一步候选（按价值排序）**

- **GPU 帧的 `shadowedPixels` 恒为 0。** 这个统计值只在软件光栅器里累加（着色时数被判为
  被遮挡的像素），Vulkan 路径没有对应的计数，所以同一场景开阴影、软件帧报 2552、GPU 帧报 0。
  0.2.1 的 `TestShadowsAcrossBackends` 因此比的是「开关阴影后变了哪些像素」，不读这个字段。
  补它要在 CPU 侧按 `mesh.frag` 的级联选择与采样逻辑重算一遍（或让着色器回读计数），前者与
  参考实现天然一致，代价是每帧多一次逐像素的深度比较。
- **GPU 的 mip 链与 CPU 的 mip 链内容不同（已定位，未修）。** `Texture::GenerateMipmaps` 对
  sRGB 贴图的 2×2 均值是“解码到线性 → 平均 → 重新编码”（`engine/src/texture.cpp:150`），
  而 `backend_vulkan.cpp` 在向 GPU 上传时用同一段暂存内存重建粗层，直接对编码后的字节求均值
  （注释写的是“the same 2x2 box the CPU sampler uses”，那只对线性贴图成立）。黑白棋盘格的
  第 N 层因此在 CPU 上是 188、在 GPU 上是 128；深色与亮色的混合差距更大。影响面是任何被缩小的
  sRGB 表面（非 `pixelPerfect` 的精灵、远处的网格面），而两条后端的像素比对目前只覆盖
  `pixelPerfect`（不采 mip）与几何边缘，所以没有用例会红。改法有两条：把 CPU 的链整体传给 GPU
  （`Texture` 的链是私有的，要先给出访问器，等于动 `cairn/texture.h` 的契约），或者在上传时
  按同样的“解码/平均/编码”重建。后者不动契约，代价是每个 sRGB 贴图上传时多几次 `SrgbToLinearFast`
  调用；无论走哪条，都要先补一条**非 `pixelPerfect`、被缩小**的跨后端用例（今天会红）。
- **GPU 上 2D 精灵的贴图采样与软件不一致。** 已在 0.2.0 关闭：根因是编辑器帧的网格线段顶点
  盖掉了 2D 顶点，与贴图、mip 和采样器都无关（关掉 `pixelPerfect`、`msaa 1`、`shadows 0` 仍差，
  是因为线段照旧在写）。复现口径保留在 0.1.34 / 0.1.35 的记录里，回归用例是
  `TestEditorFrameSprites` 与 `cli: game frames use the scene camera`。
- **过渡的插值。** 现在切换是硬切。下一步是过渡时长与淡入淡出（两个剪辑的帧按权重混合，
  或至少一个短促的交叉淡出），以及按参数连续混合的走路/跑步混合（1D blend tree）。
  混合必须同样是确定性的：权重是参数的函数，不是墙上时钟的函数。
- **`image.draw.line` 的默认笔宽。** `strokeLine` 用半径 `width / 2` 的圆盘盖章，`stampDisc` 又以 `hypot(x + 0.5 - cx, y + 0.5 - cy) > r` 剔除像素，于是 `d == r` 处覆盖率为 0：整点坐标的水平/竖直线（`--x1 0 --y1 4 --x2 7 --y2 4`，默认 `--brush 1`）什么都不画，45° 斜线只画出隔一个的像素并漏掉终点。`--brush 3` 正常。修它要换覆盖率模型（或至少把半径按 `+0.5` 处理），会让现有 `image.*` 的输出改变，所以留到能一并更新测试与文档时做：在那之前，1 px 的标记（如 2D 面板的画布）用 `imaging.fillRect` 画。
- **精灵尺寸进资产库。** 把贴图的像素尺寸与 sprite 矩形做成 `.meta` 的导入设置（`AssetMeta`
  的 `settings` 是现成的 Json），剔除与场景面板就不用为了知道大小而加载贴图，上面那条
  "仍开着"也就收口了。
- **文字清晰度**：字形 quad 已随 0.1.22 一起补全，但字号/像素对齐还没有专门的用例。

## 阶段：性能与物理（0.3）

**已做**

- 绘制预算：不透明网格与阴影 caster 都实例化；贴图走 bindless 数组，因此合批的键只剩
  「网格 + 剔除模式」。一帧的绘制数由"物体数"变成"相邻同网格 run 数"。
- CPU 并行：进程级工作池，只用在"下标无关"的地方（软件光栅化的扫描行分带、后处理、
  天空/清除），输出与串行逐位相同。
- 观测：`Profiler` 覆盖 update/scripts/physics/render/gather/shadows/raster/post/gpu，
  `engine.profile` 读出快照并附带绘制计数与任务系统遥测。
- 物理正确性：连续碰撞检测（0.1.13）。逐刚体可选（`collisionDetection =
  Continuous`），用保守推进（conservative advancement）求真实碰撞时刻，而不是固定
  采样，所以薄墙挡得住、斜向命中也不会被包围盒提前截停。默认（Discrete）路径一行
  都不改。
- 约束补齐（0.1.16）：`HingeJoint` 与 `FixedJoint`。三个关节共用同一个"点对"原语——
  把一个刚体上的世界点约束到另一个刚体上的世界点（先位置、后速度，按逆质量/逆惯量
  分摊）。点偏离质心就同时表达了转动，所以铰链 = 锚点 + 轴上一点（锁 5 个自由度），
  焊接 = 3 个不共线点（锁 6 个）。点质量矩阵是"对角 - 两个秩一项"，用 Cramer 法则
  一次解出（不是逐轴迭代），每个点对在迭代前都重新按当前变换算一次坐标——这一条是
  早期版本"自己跟自己较劲"的根因。
- 网格碰撞体（0.1.19）：`MeshCollider` 让场景能用任意 `.obj` 当关卡几何——坡道、房间、
  走廊，都是三种基元表达不了的形状。三角形在网格自身空间里存放，连同它的世界矩阵一起
  装进 `Shape`，所以旋转/父级/运动学的碰撞体不需要逐帧重建三角面。三种基元各有精确解：
  球用"到三角形的最近点"，胶囊用"线段-三角形最近点对"（端点投影 + 三条边 vs 线段 +
  线段在平面上的垂足，候选集完备所以取最小即精确），盒用 13 轴分离轴（3 个盒轴 + 面
  法线 + 9 个边叉积），取"间隙最大"的轴作接触法线，正/负都成立（分离时是间隙，重叠时
  是最小穿透轴）。射线用 Möller–Trumbore 在网格局部空间求交（局部参数再按变换尺度换回
  世界距离）；`Physics::OverlapSphere` 也走精确三角形而不是包围盒。
  两个由此免费得到的能力：**CCD 与角色控制器**。它们只依赖 `ShapeSeparation`，而
  `ShapeSeparation` 的网格分支与 `Collide` 共用同一条通路，所以 0.1.13 的保守推进
  能挡住薄网格墙、0.1.8 的角色控制器能站在网格地面上——不需要第二套代码。三角形遍历用
  "盒间隙 > 当前最优分离度就跳过"剪枝（**不能**用"AABB 不相交就跳过"：远处的三角形
  仍可能是最近的，那样会把 7.8 的分离度报成"无交互"，CCD 就直接放弃扫掠放行穿过）。
  非凸网格对"求解器要推动的刚体"没有良定义的响应，所以和 Unity 一样只允许静态/运动学：
  挂在非运动学 `RigidBody` 上时丢弃该碰撞体并在日志里报一次（刚体本身照常积分）。
  网格-网格不模拟。
 - 形状查询（0.1.20）：`physics.overlapBox`、`physics.sphereCast`、`physics.boxCast`
   （引擎里是 `Physics::OverlapBox` / `SphereCast` / `BoxCast`）把查询从"一条射线"扩成
   "一块体积"。重叠盒复用求解器同一条 `ShapeSeparation`，所以它与球、胶囊、盒、以及
   网格三角形都是精确的——不是拿形状的包围盒去比（测试专门钉住这一点：一个只切到球
   包围盒角、离球心 0.86（半径 0.75）的查询盒必须报空）。形状投射用与 CCD 同一套保守
   推进（每次前进 `separation / closing`，不是固定步长采样），只是刻意不看层矩阵——
   层矩阵是"步进"的属性，不是"查询"的属性，射线查询本来就不看。因此扫过的球/盒是
   表面在决定命中：一条从 `x=0.6` 垂直下落的射线会从边长 1 的箱子旁边漏下去打到地面，
   同位置的半径 0.5 球投射却会停在这个箱子的上边缘（法线 `(0.2, 0.98, 0)`）；`point`
   取扫掠形状自身表面上的接触点，与障碍表面在该时刻重合。起点已经重叠时返回距离 0
   （"这里已经堵住了"比"什么都没报"更有用）。顺带把 `ShapeSeparation` 盒-盒分支的
   法线朝向从"min/max 比较"改成"按质心比较"，与 `Collide` 一致——在刚好接触的临界点上
   min/max 两个条件都不成立，会退化成随便取一个方向，而质心比较不会。

   还没有异步上传或按需降级。

4. **关节补齐的下一步。** `ConfigurableJoint`（自由/锁定/限位的逐轴配置）与铰接体
   （articulated bodies，把关节链当一棵树一次性求解，而不是逐关节迭代）。

## 阶段：工具链与素材创作（0.5）

**目标。** 让 Agent 只用 `cairn` 就能把游戏素材（精灵、瓦片、图标、UI 贴图、法线图）
画到可用，并且**不依赖视觉模型就能自检**：画一笔 → 看一眼 → 改一笔。

**为什么是它。** 引擎已经有底座：`editor/main/imaging.js` 是一套零依赖的分层栅格核心
（图层、合成、笔刷/形状/填充、Sobel 法线图、PNG/BMP 编解码），CLI 用 `image.*` 把它
暴露出来。但它是**给会用鼠标的人**设计的：反馈面近乎为零（`image.info` 只给直方图，
`image.pixel` 一次一个像素，Agent 看不见 PNG 只能盲画），绘制面又缺画素材最常用的
原语（多边形、渐变、镜像、翻转/旋转/裁剪、拼合、噪声），连"填充 + 描边"都要分两次
调用，而且描边居中会向内吃掉填充。

**已做（0.1.14）**

- **反馈面。** `image.preview` 把文档（或某一层）渲染成文本：`--scale` 个像素平均成一
  格（按 alpha 加权，透明不会冲淡颜色），可以输出 ascii 亮度阶梯、`--format blocks`
  的 Unicode 密度阶梯，或 `--format hex` 每格一个 `#rrggbb`。`image.info` 在直方图之外
  新增非透明包围盒、覆盖率、是否触碰画布边缘（被裁切）、左右/上下镜像对称（含不匹配
  计数）、8 个主色（每通道 4 bit 量化），`--spans` 给出每行/每列的内容起止列；
  `--layer` 只看一层。
- **形状。** `image.draw.path`：顶点来自 `--points`（`"x,y x,y …"`、`"x,y;x,y"` 或
  JSON），或由 `--sides --cx --cy --radius --rotation --inner` 直接生成正多边形/星形；
  填充用非零环绕规则，自交的星形照样实心。`--filled` 与 `--stroke N` 可一次成型，描边
  画在形状**外侧**（`--strokeColor` 可另给描边色），所以填充不会被描边吞掉；
  `--closed false` 画折线。旧行为不变：不给 `--stroke` 时 `--filled` 仍只填充，
  `--brush` 描边仍居中。

**已做（0.1.15）**

- **对称。** 几何绘制命令（`rect`/`ellipse`/`path`/`line`/`brush`）都收 `--mirror
  none|x|y|both`：反射是按画布中心线做**几何**反射（`x → w - x`、矩形角点按
  `w - (x + width)`、`--points` 顶点逐点反射），然后拿反射后的参数再画一遍。所以镜像
  半边和原来那半边用的是同一套笔刷/填充/描边，逐像素对上；同时已经画在另一半的内容
  不受影响。`both` 是两轴都反射（等价于 180°），不是四向对称。
- **整文档变换。** `image.flip --axis x|y|both`（`--layer` 可只翻一层）按 `x → w-1-x`
  交换像素；`image.rotate --degrees` 顺时针转 90 的倍数（90/270 会交换宽高），非 90 倍数
  报 `invalid_arg`；`image.crop --x --y --width --height` 先夹到画布内再裁剪，并回报实际
  用的矩形。三者都作用于所有图层（它们共享同一张画布），图层栈不变，之后
  `image.save` 直接写出变换后的图。
- **拼合。** `image.stamp` 把一张 PNG/BMP（`--file`）或同一文档的另一层（`--from`）
  贴到目标图层（`--layer`，默认顶层）的 `--x/--y`（允许负数，超出画布的部分被裁掉）：
  `--scale` 最近邻缩放、`--opacity` 乘 alpha、`--blend over|replace`。`over` 是真正的
  source-over 合成（也写回正确的 alpha），`replace` 连 alpha 一起拷贝——所以拿一张全
  透明的图去 `replace` 会**打洞**，而不是什么都不做。源是另一个图层时先复制一份再贴，
  因此源和目标同一层也不会涂抹。精灵图 = 一张 `image.new` 画布 + 每个格子一次
  `image.stamp`。
- **反馈面修正。** `image.preview --format hex` 的透明格补齐到 7 字符宽：以前一个色格是
  7 字符而透明格只有 1 个，凡是含透明的行都会比邻行短，网格整体错位——而那正是 Agent
  用来看拼出来的精灵图的行。现在整张表的宽度恒定（`--empty "."` 可显式标出空格）。

**已做（0.1.18）**

- **种子噪声，纯函数。** `image.draw.noise --kind value|white|fractal --seed N`：整个场是
  `(seed, 坐标)` 的纯函数（整数哈希，不碰 `Math.random`，没有时间或隐式状态），所以同一份
  生成器能逐位复现、两个版本的生成器可以直接 diff。`value` 是平滑斑块、`white` 是逐像素
  颗粒、`fractal` 是多个倍频叠加（`--octaves --lacunarity --gain`，晶格尺寸 `--cell`）；
  `--from/--to` 是颜色带的两端，`--x/--y/--width/--height` 可选区域（默认整张画布）。
- **`--tile` = 无缝瓦片，而且可验证。** 打开后每个倍频的晶格都被吸附成"横跨画布整数个
  格子"，于是场在画布尺寸上**严格周期**，左右两列的关系与图上任意相邻两列一样近。测试量的
  就是这个：接缝两侧的差 ≤ 图内相邻列的最大差；不加 `--tile` 时两条边互不相干（seed 4 下
  约 98 级 vs 3 级）。"无缝"只有能被量出来才算验收。
- **渐变。** `image.draw.gradient --kind linear|radial`：线性轴过画布中心、长度是画布在该
  方向上的跨度（所以任意角度下对角都落在 0 和 1，CSS 的约定），`--angle 90` 上→下、
  `--angle 0` 左→右，也可以给 `--x1/--y1/--x2/--y2` 显式端点；径向从 `--cx/--cy` 到
  `--radius`（默认画布中心、较短边的一半）。和噪声共用同一套颜色带 / 区域 / 不透明度参数。
- **颜色带用直通 alpha 的 source-over 合成**（`compositePixel`，与 `image.stamp`/合成同一
  套公式），不是笔刷那套"取较大 alpha"：`--opacity 0.5` 盖在 50% 的像素上真的变成 75%，
  而不是留个洞或忽略底下。
- **调色板。** `image.palette`：中位切分量化（`--colors`，1–256）或吸附到给定调色板
  （`--palette "#1a1c2c,#5d275d,…"`），`--dither none|ordered|floyd`。直方图先塌缩成"不同
  颜色 + 计数"再做切分，所以平涂精灵出来的就是它自己那几个颜色（不会有重复项）；盒子按
  **跨度最大的通道**切、按人口取中位；Floyd–Steinberg 把误差扩散到右侧与下一行，ordered 用
  4×4 Bayer 阈值按调色板自身的平均步长抖动；两者都是"每像素一个阈值/误差、三通道共用"，
  所以抖动不会偏色。全透明像素不参与量化，半透明像素保留自己的 alpha。
- **`--list` 是给 Agent 的自检面。** 只报告不修改：调色板 + 每个颜色多少像素（平涂图就是
  精确计数）；配 `--palette` 用时报告"这些像素会怎么分到我的调色板上"。至此 0.5 的"画 →
  自检 → 改"里，自检不只有形状（`image.preview`/`image.info`），还有颜色。

**已做（0.1.21）**

- **闭环文档，而且可执行。** `docs/drawing.md` 把"画 → 自检 → 修正"完整走两遍，用的就是
  两个自检面：`image.preview`（`--scale 1` 下每像素一个字符的文本图）与 `image.info`
  （包围盒、覆盖率、镜像对称 + 失配像素数、主色、边缘裁切，`--spans` 给逐行逐列范围）。
  金币精灵那遍是一次**真的收敛**：矩形高光把硬币上沿削平 → 预览里第 7 行整条高光、
  `image.pixel` 在 (16,7) 读到高光色而不是body色、`image.info` 给出
  `mirrorTopBottom: false`（20 个像素失配）→ 换成椭圆高光加 `--mirror y`（关于画布中心线
  反射并同一次画完）→ 两条镜像都 `true`、失配 0。教程也点明五角星（金币的经典图案）会
  正当地让 `mirrorLeftRight` 变 `false`：对称是**报出来的检查**，不是强制。
- **瓦片的缝是量出来的。** `--tile` 把每个倍频的晶格吸附成整数格 → 场在画布尺寸上严格
  周期；逐像素的 `white` 噪声不会，教程给了抓住它的那张表（第 11 行跨接缝跳 26 个灰阶，
  而图内相邻列最大只差 20），以及修法（换成一个小的、带 `--tile` 的 `value` 晶格，之后
  每条接缝都不超过图内相邻列差），量化后再量一次证明没把缝重新打开。
- **两份配方由测试逐步重放**（`test/cli.js` 的 `cli: drawing tutorial`）：预览行、像素、
  镜像统计、接缝表、调色板报告、磁盘上真实的 32×32 PNG，以及"同一批重跑字节相同"。
  教程因此不会和实现漂开。README 的文档表也指向它。
- **顺带修掉写教程时暴露的 bug。** `blendPixel` 把半透明笔触和"透明像素的 RGB"按
  `src * a` 混合：透明底上没有可插值的颜色，旧公式却仍把源色乘上自己的不透明度存下来，
  于是 50% 白的填充在空图层上存成**50% alpha 的灰**，`composite()` 再暗一次——铺在不透明
  黑底上得到 **25% 灰**而不是 50%；同一处高光放在自己图层上（`#ddca8d`）也比直接画在
  本体层上（`#fde9a4`）更暗，写教程的第一遍就是这么撞上的。修法：颜色按**目标自身的
  alpha** 加权，`(src*a + dst*dstA*(1-a)) / max(dstA, a)`（直通 alpha 存储），目标不透明时
  与旧公式逐字节相同，所以既有绘图行为一个不变；alpha 仍取 `max()`，重复笔触或镜像绘制
  不会累积覆盖率。

## 已知限制

- **0.1.5 的 Windows/MSVC 路径无法在本机（Linux）验证**，只能靠代码审查和 CI 覆盖。0.1.24
  把 CMake 之后的产物布局、暂存与加载修好，并用 `-G "Ninja Multi-Config"` 在 Linux 上守住
  同一类多配置布局（`test/build.js` 与 `multi-config` 任务），但 MSVC 的编译与链接本身仍只能
  在 CI 上验证，因此 `windows` 任务保留 `continue-on-error: true`。
- **bindless 表是软上限。** 场景路径的贴图数组各 512 槽；一帧里引用的
  `(贴图, 采样器)` 对超过这个数量时会抢占最近最少使用的槽位（画面退化为槽位抖动），
  单帧真的超过 512 对时多出的绘制会取到白色贴图。这是刻意选择的降级方式：不崩溃、
  不静默丢贴图。
- **描述符索引是硬性设备要求**（`descriptorIndexing` 等）。不满足的设备会回退到软件
  路径并在日志里给出原因。
- **CCD 只扫平移，不扫旋转。** 高速旋转的细长物体仍可能把角速度扫进障碍。目标也只
  限于实体静态/运动学碰撞体（对应 Unity 的 `CollisionDetectionMode.Continuous`，
  不是 `ContinuousDynamic`），两个都开了 CCD 的动态物体之间仍是离散处理。保守推进
  迭代上限 32 次，掠过式逼近会安全地提前停住。
- **CCD 不接住「先接触、再被赋高速」的物体。** 步首已经贴着的障碍会被当作既有接触
  交给离散窄相（否则躺在地板上的物体会读到零碰撞时刻，连滑动都会被冻住）。因此一个
  已经贴着墙的刚体，如果脚本在同一步把它的 `velocity` 写成指向墙内的大值（或
  `AddImpulse`），那一步会穿过去——正常流程里接触冲量早就把法向速度清零了，只有脚本
  直接改写才会造成这个状态。
- **关节的已知边界（0.1.16）。**
  - **被关联的刚体不要放在带旋转的父节点下。** 与积分器一致，关节把
    `Transform::rotation` 当作世界旋转读，点对的速度/惯量都按"质心在世界原点 +
    旋转就是世界旋转"算。父节点只有平移、或旋转为 0 时完全正确；带旋转的父节点下，
    关节会按父节点的世界旋转去解释子节点的"局部"旋转，结果是偏的。
  - **限位与马达的基准是"第一步捕获的位姿"。** 限位角度从关节第一次求解时（即该步
    积分之后）的位姿起算：如果刚体在第一步就以匀速运动（脚本在步前写好了
    `velocity`），基准会带着这一步的转角。正常情况下（先摆好静态位姿再启动）基准就
    是作者摆的位姿。
  - **马达需要 `motorForce > 0`。** 力为 0 视为关闭（Unity 语义：力上限就是"能不能
    驱动"）；`motorVelocity` 是度/秒，正的转"能被驱动的那一端"。
  - **休眠的刚体不受关节约束。** 与整个步的休眠语义一致：两端都睡着时关节这一步不
    求解，所以把睡着的刚体直接传送走不会立刻被拉回——给它一点速度（或让装载量超过
    阈值触发唤醒）即可。
  - **`FixedJoint` 没有锚点。** 它焊接的是捕获时的相对位姿，所以要把两个物体摆到想要
    的相对关系再去加关节；加完之后移动其中一个，另一个会被拖着走（这是设计行为）。
- **预制体覆盖的已知边界（0.1.17）。**
  - **节点按"名字路径"配对，不是身份。** 在实例上重命名或换父会让该节点脱离模板：旧名字
    被记为 `@removedChildren`，节点本身作为"实例新增"保留，之后不再跟随资产。Unity 用
    资产内 fileID + 实例映射，这是把这块做扎实的地基（见"下一步候选"）。
  - **同名同级节点按出现顺序配对。** 两个同名兄弟互换位置会被读成"两者都改了属性"，而不是
    "顺序变了"——顺序本身不进记录。
  - **资产侧的删除不会传播到别的实例。** 从 `.prefab` 里删掉节点/组件后，没有 `@removed*`
    记录的实例会按模板把旧结构重建回来，直到 `prefab.revert`。
  - **实例新增的组件/子节点只被"保留"，不进记录。** 在实例上新加的组件/子节点是一次性的：
    sync 不会删它，也不会维护它；如果之后资产也加了**同类型**组件，那次同步会把这个实例
    新增组件的属性也按资产值覆盖（除非对应属性已在记录里）。
  - **`@removed*` 只对设置它的那一个实例生效**，资产与其他实例不受影响。
  - **判定粒度是 1e-6（相对）/ 1e-9（绝对）。** 比这更小的改动不会被记为覆盖，于是回填时
    会被资产值取代；设这个容差是为了让"文件被读回来"不产生噪声，正常手工或脚本编辑远大于它。
- **图形工具的 `--stroke` 与 `--brush` 语义不同。** `--stroke N` 的描边整体画在形状
  外侧（这是让"填充 + 描边"不互相吃的前提），而 `--brush N` 是旧行为、描边居中，两者
  都保留；新脚本用 `--stroke`。
- **外侧多边形描边是 miter 偏移（上限 4×）。** 尖角会被切平；高度自交的多边形偏移后
  可能自相交，此时按"偏移多边形 − 原多边形"的同心环绘制，仍是形状外一圈，但不保证
  严格等宽。`image.preview --scale` 是块平均而不是重采样，所以一格里的颜色是那块像素
  的平均值，不代表其中任何一个像素。
- **`--mirror` 只按画布中心线反射，没有任意镜轴。** 要绕别的轴镜像就先画在对称位置，
  或用 `image.crop` 把画布中心挪到目标轴上。`both` 是两轴各反射一次（180°），不是四向
  对称；奇数边长画布的中心列/行是自己的镜像。
- **`image.rotate` 只支持 90 的倍数。** 任意角度旋转需要重采样与插值，目前只有最近邻的
  `image.resize` 和 90 度整转；90/270 会交换宽高，`crop` 会把矩形夹到画布内（也就是说
  裁出来的尺寸可能小于请求值，返回值里给的是实际矩形）。`image.stamp --scale` 同样是
  最近邻，不滤波。
- **纹理素材的已知边界（0.1.18）。**
  - **`--tile` 会吸附 `--cell`。** 为了让周期严格等于画布尺寸，每个倍频的格子数取
    `round(边长 / cell)`，所以 32 px 上 `--cell 10` 实际是 10.67 px。`--kind white` 下
    `--tile` 是空操作（逐像素独立本来就没有接缝），返回值里的 `tile` 会如实报 `false`。
  - **噪声与渐变用的是直通 alpha 的 source-over，笔刷路径仍是"取较大 alpha"。** 前者是
    "填一块区域"该有的合成，后者是 0.1.14 之前就有的笔刷行为，没有改动（纯增量）。两张
    图叠在一起时这才会显出差别。
  - **径向渐变的默认半径是 `min(w,h)/2`，不是到最远角的距离**，所以默认情况下四个角都
    已经被夹到 1（纯色）；想要"到边角刚好结束"就显式给 `--radius`。线性渐变的角度是按
    画布在该方向上的跨度铺满的（45° 时对角距离最长），不是按像素距离。
  - **调色板量化只碰 RGB。** 全透明像素完全不参与（也不改），半透明像素按 RGB 归到最近
    的颜色、alpha 原样保留；中位切分把直方图塌缩成不同颜色后切分，所以一张照片式渐变图
    的分色是"颜色空间里均匀"的，不是感知均匀（没有用 Lab/OKLab）。`--list` 会忽略
    `--dither`（报告的是不抖动的落点）。
  - **抖动是全图一次遍历。** Floyd–Steinberg 按行从左上到右下扩散，误差表只有两行（不
    保留整图误差），所以同一张图分块绘制与整块绘制的结果不完全相同；ordered 是逐像素的
    4×4 Bayer，与其他像素无关。
- **网格碰撞体的已知边界（0.1.19）。**
  - **三角面汤没有 BVH。** 每个候选对的窄相位遍历网格的**全部**三角形，唯一的剪枝是
    "三角形包围盒与对方包围盒的间隙已经大于当前最优分离度"。所以它适合关卡几何，不适合
    十万面的模型；大网格请先切成多块，或等一等 BVH。（这也是 0.1.19 唯一一处 O(n) 的
    地方：宽相位仍是 X 轴 sweep-and-prune。）
  - **只在静态/运动学物体上生效。** 非凸网格对"求解器要推动的刚体"没有良定义的响应
    （Unity 同样禁止非凸 MeshCollider 配非运动学刚体）。挂在非运动学 `RigidBody` 上的
    `MeshCollider` 会被丢弃，并在引擎日志里**每个碰撞体只报一次**（上限 128 条，避免刷屏），
    刚体本身照常积分下落。**网格-网格不模拟**，两个 `MeshCollider` 互相穿过。
  - **没有凸包（`convex`）。** Unity 的 MeshCollider 有个 `convex` 开关，勾上后能当动态
    碰撞体用（内部走凸包 + GJK/EPA）。这里没有实现：既没有凸包生成，也没有 GJK/EPA。
    这是"网格碰撞体能被推"的唯一缺失环节。
  - **法线假定接近均匀缩放。** 三角形和包围盒按完整变换走（所以非均匀缩放的**位置**是准
    的），但射线命中处的法线用 `meshWorld` 变换方向而不是逆转置矩阵，因此非均匀缩放会让
    法线有偏差——与球/胶囊碰撞体用 `WorldMaxScale` 的既有取舍一致。
  - **"在闭合网格内部"走的是三角面汤语义。** 没有内外判定：一个整体落在闭合凹网格内部的
    物体会被推向**最近的那个三角形**（也就是最近的面），而不是从最近的出口推出去。落在
    面上、穿墙、上坡这类用法都精确；把物体"塞进"实体内部不是。
  - **另一边只支持三种基元。** 球、胶囊、盒（盒在窄相位里就是 AABB，和 0.1.4 起的一致）。
    `Collider2D` 永远不与网格交互（2D/3D 不混），`CharacterController` 的胶囊可以直接站在
    网格地面上。
  - **网格按绝对路径缓存、不跟着 `.obj` 的变化走。** `MeshLibrary` 以绝对路径为键缓存已
    解析的网格，重导入/扫描资产时才会清空；在编辑器外手改 `.obj` 后需要一次资产扫描
    （或重启会话）才能看到新三角形。
- **2D 的上下朝向已收口（0.1.23）。** 约定是**图像的上边 = 世界的上边**：贴图第 0 行是
  `v=0`，`image.*` 的 y=0 是上边，所以画在图上半部分的像素出现在精灵/字形的上半部分。
  `flipY` 现在就是"把已经画好的图上下反过来"，语义与这个约定一致。法线图的绿通道一并定了：
  `image.normalMap` 按图像空间编码（G<0.5 表示法线朝图像上方＝世界上方），`sprite.frag`
  与软件精灵路径里的 `-(绿通道)` 因此正确，`TestSpriteNormalOrientation` 把它钉住。
- **3D 网格贴图的 v 轴还没核对（0.1.23 未动）。** 软件网格路径的法线图重映射和精灵路径
  共用同一句 `-(绿通道)` 和同一段注释（"top-down v"），但 3D 的贴图 v 来自 OBJ 的 vt
  （惯例是 v-up），与 2D 的图像空间并不是同一套。网格贴图是否也上下反、法线图绿通道要
  不要跟着改，需要一个带真实贴图的 `.obj` 用例来定，还没有做。
- **精灵的剔除边界要先知道贴图像素尺寸（0.1.26）。** 精灵的世界尺寸是"uvRect 的像素 /
  pixelsPerUnit"，而像素数只有贴图自己知道，所以 gather 阶段必须先解析贴图才能剔除：
  一个完全离屏的精灵也会把贴图加载一次（之后 LRU 会留着，但预算淘汰后下一帧可能再加载）。
  只要不是"离屏精灵 + 贴图预算吃紧"同时成立就无感。彻底的解法是学 Unity，把尺寸做成
  导入结果写进 `.meta`（`AssetMeta::settings` 已经是能装它的 Json），列在 0.2 的候选里。
  文字不受影响：它用自身字号与文本长度估边界，这个估计只会偏大，不会误剔。
