# Changelog

All notable changes to Cairn Engine are documented here. Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/); versioning follows [SemVer](https://semver.org/).

## [0.2.3] - 2026-10-25

### Rendering: a GPU frame costs what the GPU takes, not what reading it back costs
- **Eighteen to twenty-one milliseconds of a 1080p Vulkan frame went to copying pixels the GPU had already finished.** The backend renders offscreen and reads every frame back through one staging buffer, and `CreateBuffer` asked for `HOST_VISIBLE | HOST_COHERENT` only. On a desktop GPU that is the uncached BAR heap: the host read of a 1920x1080 colour buffer plus its depth buffer runs at about 0.5 GB/s, so 30.8 ms of a 31.5 ms frame was two `std::memcpy` calls, and the fence wait measured 0.00 ms because the GPU had long since finished. A simple ground plane and cube ran at 31.8 fps on Vulkan against 41.9 fps on the software rasterizer, which is the shape of the complaint: the GPU path was slower than the CPU path. Instrumenting the four stages (record / submit / wait / copy) put 98% of the frame in the copy.
- **The readback buffer now asks for host-cached memory when the device has such a heap.** `HOST_CACHED` is a preference, not a requirement: the selection is a two-pass search for `HOST_VISIBLE | HOST_COHERENT | HOST_CACHED` and then `HOST_VISIBLE | HOST_COHERENT`, so a device that exposes no cached host heap allocates exactly what it allocated before. The same frame now costs `0.2 ms` at 640x360, `0.7 ms` at 1280x720 and `1.5 ms` at 1920x1080 - 17x, 20x and 21x - and the fence wait and the copy are both under a millisecond, which is what a frame whose geometry, shadows and post chain took the GPU a fraction of a millisecond should cost.
- **The pixels are identical.** The frame the cached buffer carries hashes to the same SHA-256 as the frame the uncached buffer carries (`70d6c55405f05a71c5292bc6...`, a 1280x720 game frame of the 3D template, hashed after a 100-frame run), and the same run takes 0.63 ms against 14.34 ms. The three cross-backend tests that compare GPU and software pictures are unchanged.
- **The selection is a pure function, so it is tested without a GPU.** `engine/src/vulkan_memory.h` now holds `SelectType(mem, typeBits, want, prefer)` and `SelectStagingType(mem, typeBits, cached)`: the first pass asks for `want | prefer` and the second drops `prefer`, which is the semantics the image and texture paths already relied on (a device-local heap that would rather be host-visible). Every allocation site in the backend goes through it, including the buffer, image and texture paths, with the existing choices preserved bit for bit. `TestVulkanReadbackMemory` builds six synthetic heaps - device-local, both host heaps, and three decoys that carry one of the three required properties but not the others - and pins the cached heap winning, the coherent heap when caching is not asked for, the cached-but-unmappable and coherent-but-unmappable heaps never being chosen, the unasked-for preference being dropped when the device has no cached heap, and a device with no device-local heap reporting no answer rather than a host heap.
- **`TestVulkanReadbackSeesLatestFrame` pins the hazard the faster heap introduces.** A cached mapping that went stale would freeze the viewport on the first frame; a mapping that tore between frames would show it as noise. The test renders a frame twice with nothing changed, requires both buffers to repeat pixel for pixel, moves the camera on both axes, requires a substantial change in colour and in depth, then returns to the first position and requires the first frame back exactly. Six mutations of the selector were applied, built, observed to fail and reverted: dropping the cached preference (2 checks), dropping the host-visible requirement (4), removing the `typeBits` filter (12), promoting the preference to a requirement (3), deferring the preference to the second pass (4), and dropping the coherence requirement (4). The backend was also run with `VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`; the layer is loaded and reports (a standalone program that leaves a buffer alive produces its VUID message), while the engine produces no message.

## [0.2.2] - 2026-10-24

### Build: the addon finds Node's headers and node.lib in the installation that has them
- **`npm run build` on Windows reported "node headers not found" on a Node that may well have had them.** `nodeIncludeDir()` checked exactly two paths beside the interpreter that ran the script, `<node>/include/node` and `<node>/../include/node`. A Node installation lays its headers out in more than one shape - `<root>/bin/node` (a distro package, nvm, fnm), `<root>/node.exe` (the Windows installer), `<root>/<arch>/node.exe` (a runner tool cache) - and the interpreter npm runs need not be the installation the build should use. The failing step was the addon's, and it stopped the Windows build after the engine DLL had already produced, which made the failure look like a missing SDK rather than a search that was too narrow.
- **One discovery answers both halves.** `findNodeDevInstall({execPaths, env})` walks the ancestors of the interpreter *and* of every `node` on PATH (`nodeExePaths`), and honours `NODE_ROOT_DIR`, `npm_config_nodedir`, `NVM_HOME`/`NVM_SYMLINK`, the Windows `Program Files`/Chocolatey install paths and the node-gyp cache. `node_api.h` is the marker, because that is the header an N-API addon compiles against; `node.lib` and `lib/node.lib` are read from the same roots, so the Windows link path takes its import library from wherever the headers were. A failure now names what was searched instead of repeating the one path that was not searched, and a successful build logs `[cairn] node -> headers ... / lib ...`.
- **Tests.** `test/build.js` grows to **19 checks** with a `build: node development install discovery` section over synthetic trees: the versioned layout (tool cache), the `bin/` layout (distro, nvm), the flat layout (Windows installer, via `NODE_ROOT_DIR`), the import library, the absence report, and the searched-roots list. Four mutations were applied, built, observed to fail and reverted - limiting the ancestor walk to the executable's own directory (3 checks), changing the marker file (3), ignoring the environment overrides (1), and accepting a root without `node_api.h` (3). Each run used the same fake trees, so no compiler is needed.
- **CI.** The Windows job prints `process.execPath` and the contents of its directory before the build, so the next failure of this step names the layout instead of the search.

## [0.2.1] - 2026-10-24

### Rendering quality: shadows on the GPU, and the seams between triangles
- **A directional shadow reached the depth map and never reached the frame on the GPU.** `shadow.vert` negates clip-space y before rasterising a cascade, so the depth pass writes top-down rows, `(1 - (ndc.y * 0.5 + 0.5)) * size` - the orientation the software pass writes too. `sampleShadow` in `mesh.frag` looked up `(ndc.y * 0.5 + 0.5) * size`, the mirror image of the map, and found free depth at every point, so the comparison passed and no surface was darkened. The software path drew the shadow, `TestShadows` only ever rendered in software, and no test compared the two masks: a complete failure of the feature stayed green. On a 400x300 game frame of `project-3d`, 2983 pixels were more than two levels away from the software reference; with the row flipped the GPU lays the shadow down where the reference does. The mask was checked across the shipping settings - cascades 1, 2 and 4 at `shadowDistance` 30 and 60 on a 320x240 frame: software 841 to 1065 lit-shadow pixels, GPU 828 to 978, centroids within a pixel of each other.
- **Every shared interior edge of a mesh carried a one-pixel dark line.** `RasterTriangle` discarded any pixel whose centre fell outside the triangle, so the pixel straddling an edge belonged to neither of the two triangles that share it and kept the background showing through. The Ground plane of a new 3D project is two triangles with one diagonal, and the line ran across its whole face - 311 pixels on that frame. Coverage is now computed before ownership is decided, and a triangle also owns the pixels whose centre lies up to half a pixel outside one of its edges, which is exactly the area it covers there. The strict centre test remains for `antialias == false`, so the hard-edged path is unchanged.
- **Half-covered pixels were blended over each other.** A pixel an edge crosses is filled twice when two triangles of the same surface claim it, and plain source-over compositing darkened it by the background each triangle left uncovered. A partially covered opaque pixel now adds `share * (src - background)` over the sky-only frame captured at clear time (`aaBackground`), with `share = min(coverage, 1 - aaCover[pix])` and `aaCover` accumulating the covered area - so three triangles meeting at a corner cannot fill the pixel twice either. A fully covered pixel still composites source-over. Dark-seam pixels on that frame: 311 to 0, and the count of pixels more than two levels away from the GPU fell from 1661 to 866.
- **A sprite had the same seam along its own diagonal, and it was stronger.** `mat.blend` items were composited per triangle: the two triangles of a sprite quad each blended their half-covered diagonal pixel separately, so both halves applied the background a second time and a faint dark line crossed the sprite. It was visible on any sprite with edge coverage on - that is, every sprite that is not pixel-perfect. The 2D loop now marks its materials `item2D` and clears the coverage of the previous item over the same triangle bounds (`ClearItemCoverage`), so the two triangles of one quad fill a pixel once: each adds its share of the quad's colour over the colour underneath the item (`aaBlendBg`), captured where its first triangle touches the pixel. On a white sprite rotated 30 degrees over black, the middle row held 172 where the quad is 196; it now holds 196 across the whole row.
- **Tests, on the pictures rather than on the stats.** `TestShadowsAcrossBackends` renders the same scene with shadows on and off on both backends and takes the region that changed as the shadow: the software count must exceed 200 with a centroid below the caster, and the GPU must match it within 25% of area and 3 pixels of centroid - an unmirrored lookup fails all three. `TestInteriorEdgeAntialiasing` fills a 160x120 frame with an unlit plane seen face-on: every pixel must be the surface's own colour, with none darker or brighter, which fails on either half of the fix. `TestSpriteEdgeAntialiasing` draws a rotated sprite over black and requires its middle row - the row the shared diagonal crosses - to be uniform at peak brightness while the silhouette outside it still has intermediate values, and fails when per-quad compositing is forced off. `TestCullingAndAA`'s quad shrank from 6 to 2.5 units so its antialiasing check counts silhouette pixels rather than the seam that no longer exists. No CLI command changed: 529 checks.
- **Confirmed non-vacuous, three mutations.** Restoring the unflipped `fy` fails the three GPU shadow checks; restoring the centre-only ownership test fails `darker == 0` plus `TestCullingAndAA`'s culling counts; forcing `perQuad` off fails `seam == 0`. Each was applied, built, observed to fail and reverted, and the suite was run under `VK_LAYER_KHRONOS_validation` with a clean report.
- **Left open.** The backends now differ on 862 of 120000 pixels of that 3D game frame, and what remains is the half-pixel convention at silhouette edges (the GPU samples at pixel centres the software path treats as outside), not geometry or shadows; a point light and a spotlight each leave about 0.5% of a 320x240 frame more than two levels apart, and the post-processing chain (bloom, vignette, contrast, saturation) about 0.8% with a mean under one level. `RenderStats.shadowedPixels` is still computed by the software path only, so a GPU frame reports 0 even with shadows on; the new test compares pictures instead of that number, and the stat wants a GPU-side count.

## [0.2.0] - 2026-10-23

### Rendering quality: 2D sprites, and game frames that used the editor camera
- **Every editor frame drew the sprites out of line vertices.** `RenderScene` staged a frame's 2D vertices into `lineVerts` at offset zero and then staged the frame's debug lines into the same buffer at the same offset. The editor grid *is* debug lines, so every editor frame wrote about 4.5 KB of line vertices over the sprite vertices before the command buffer was submitted; the sprite pass then read those bytes as `Vertex2D` (48 vs 28 byte stride) and the quads collapsed into slivers across the middle of the frame - sprites vanished, came out as thin vertical stripes, or painted near-black over whatever should have been visible there. Play frames carry no lines, which is exactly why the software rasteriser and every 2D test looked right while a `project-2d` scene view was garbled: the tests compared game frames. On the same 400x240 editor frame of that project, pixels more than two levels away from the software reference went from 22010 to 2205, and 80% of what is left sits on a strong edge in the reference (15 to 25 pixels per row, none structural); the play view of the same project agrees with the reference within 2 pixels of 96000.
- **The two vertex streams are separate buffers.** `verts2D` (48-byte quads for sprites and glyphs) and `debugVerts` (28-byte segments) are now distinct host buffers with their own copies and their own bind points, so a frame can carry both without either owning the other's memory. The second memcpy is gone rather than moved: the lines are staged once, next to the 2D vertices, before recording. The rename from `lineVerts` to `verts2D` is part of the fix - outside the frames that clobbered it, that buffer never held a line.
- **`--mode game` rendered through the editor camera.** `Engine::BuildCameraView` consulted `scene_->MainCamera()` only while `playing_` was true, and `RenderGameFrame` fell back to `RenderEditorFrame()` - grid and selection outline included - whenever it did not. A game screenshot taken outside play mode was therefore the viewport: two shots of the same scene with the MainCamera at `(0,0,10)` and at `(100,0,10)` were byte-identical, which is how the fault was found. The camera choice is now an explicit argument, `BuildCameraView(out, useSceneCamera)`: `false` for the editor view and for the screen-space helpers, which keep following the game camera during play, and `true` for `RenderGameFrame`, which also stops drawing the grid in its no-camera fallback. `RenderStats.camera` names the camera that produced the frame - `"scene"`, `"editor-fallback"` or `"editor"` - and reaches the CLI through `StatsToObject`, so a screenshot says which camera it came from.
- **Tests.** `TestEditorFrameSprites` renders an editor frame, grid lines and all, with a checker sprite: all four quadrants must be covered, the interior must hold the two texel colours and nothing else, and more than 4000 pixels must be lit. Line vertices cannot do that - the mutation section below is the same test failing. `TestRenderGameCamera` pins the camera contract on both backends: the game frame follows the MainCamera (the quad is present with the camera at the origin and gone with it at `x = 60`, while the editor frame still shows it), the stats name the camera, and a scene with no camera reports `editor-fallback` and still carries no grid - the editor frame in the same pose has more than 100 grid-coloured pixels and the game frame fewer than 5. The CLI grew 517 -> **529 checks** with a `cli: game frames use the scene camera` section: a red sprite on black, the game shot flat red at a single palette entry, black once the MainCamera turns away, the editor shot byte-identical across that move, and the three `camera` values.
- **Confirmed non-vacuous, four mutations.** Staging the lines back into the 2D buffer fails `colours.size() <= 3`; returning `RenderGameFrame` to `playing_ ? MainCamera : editor` fails eight engine checks and four CLI checks, including the fallback's grid check. Each was applied, built, observed to fail and reverted.
- **Left open.** The software rasteriser still draws the editor grid's spokes across the faces of a mesh that should occlude them (0.1.35), and the two rasterisers disagree on 2205 of 96000 pixels in a sprite-heavy editor frame - sparse differences at texel and grid-line edges, which is what nearest sampling of minified content does when a texel boundary lands on a different side of a pixel centre. Mip chains are also built differently on the two paths: `Texture::GenerateMipmaps` decodes sRGB to linear, averages and re-encodes, while `backend_vulkan.cpp` rebuilds the coarse levels from encoded bytes, so a minified sRGB sprite samples a darker chain on the GPU. No test compares those levels yet; it is recorded under candidates in `docs/roadmap.md`.

## [0.1.35] - 2026-10-23

### Rendering quality: Vulkan draws the front faces of a mesh again
- **The default cube of a new 3D project came out inside-out on the GPU and every suite stayed green.** Opened in the editor, a `project-3d` scene showed a cube whose top was as dark as its sides and a bright quad lying on the grid at its base; the software rasteriser, which is the reference, drew the same entity with a lit top and two dark sides. `8982` pixels of that 320x200 frame were more than two levels away from the reference, `15602` differed at all, and the cube still counted as "lit" for `TestRenderBackendsAgree` - the cross-backend test compares the lit-pixel count within a factor of two, which a mesh rendered inside-out satisfies.
- **The pipeline's winding declaration contradicted the vertex stages.** `CreatePipelines` declared `VK_FRONT_FACE_CLOCKWISE` - the value a renderer wants when it leaves clip-space y alone - while `mesh.vert` and `shadow.vert` both negate `p.y` to keep +y up in Vulkan's y-down framebuffer. Vulkan decides facing from the winding it reconstructs in *framebuffer* space, so negating y in clip space reverses that orientation: the declaration made every engine-side front face a Vulkan back face, `cullMode` (back by default) discarded the near faces, and a closed mesh drew its interior. For a cube that is the inside of its bottom face where the top should be - the bright quad at the base - with the far sides' normals shading what the camera sees. `VK_FRONT_FACE_COUNTER_CLOCKWISE` is the declaration the shaders actually describe; with it the cube's pixels land on the reference's values (a lit top of `cfcfd0`, sides of `595b5e`) and the count of pixels more than two levels off drops from 4066 to 2219 on that frame.
- **Unlit was a CPU-only word.** `MeshRenderer.unlit` was honoured by `Renderer::ShadeAndStore` and ignored by `mesh.frag`, which never read `flags.x`. The same material was flat in software and lit on the GPU, so an unlit mesh in a scene without lights was black on one backend and its own colour on the other. `mesh.frag` now takes the unlit branch before the ambient/light/specular block, hands the albedo to the shared tonemap and skips emissive, matching the CPU branch line for line.
- **One quad pins both halves.** `TestRenderFrontFace` draws a green `Quad` facing the editor camera and counts green-dominant pixels, so neither the grid nor the sky can be mistaken for the mesh: `CullMode::Back` keeps it above 200 pixels and `CullMode::Front` drops it below 20, on both backends; the same quad with `unlit` set reaches the frame bright (above 200) while the lit one under an ambient of 0.1 stays dim (below 20). The winding half uses an emissive material so it does not depend on the unlit fix, and the unlit half culls nothing so it does not depend on the winding fix.
- **Confirmed non-vacuous, three mutations.** Restoring `VK_FRONT_FACE_CLOCKWISE` fails `drawn > 200` and `culled < 20` - the quad is culled in both directions; deleting the unlit branch fails `unlitPixels > 200`; forcing the branch on fails `litPixels < 20` and `TestSpriteOrientation`'s unlit-text checks. Each was applied, built, observed to fail and reverted.
- **What is left in the frame.** After the fix the remaining differences on the same `project-3d` frame are the grid's spokes and one-to-two level rounding in the sky and ground gradients, plus the software path painting those spokes across the cube's faces where the GPU occludes them. The shadow pass shares the corrected declaration, so it now rasterises front faces like the colour pass and no acne appeared against the reference.
- **Left open.** The 2D sprite path is still wrong on the GPU, and it is a different fault: on a `project-2d` scene the sprites sample near black (`22,20,20` where the reference has the ground's `155,156,162`) instead of the atlas contents, which is the candidate `docs/roadmap.md` carries with its repro. `TestRenderBackendsAgree` still compares only a lit-pixel ratio, so neither bug would have been caught by it; the new test covers the mesh path's winding and the unlit flag and nothing else.

## [0.1.34] - 2026-10-18

### Tooling: a project opens with its gameplay scripts built and loaded
- **A new 2D project could not move, and the console said so in the engine's words.** A `Script` component resolves its class by name when the game starts, and a class only exists in the process after the library that registers it is loaded. The editor had no path that did that on its own: only an explicit **Build Scripts** compiled and loaded, so a freshly created `project-2d` opened, played, and logged `script class not found: Player2D (build scripts first)` - a statement about the engine's state, not about the button that fixes it. It was reproducible from a clean template and the workaround (build, then play) worked, which is exactly what made it a missing lifecycle rather than a broken script.
- **One pure function decides staleness.** `scriptStatus` in `editor/main/build.js` compares `Library/GameScripts.<ext>` against everything under `Assets/Scripts` and answers with one of four states: `nosources` (nothing to compile), `missing` (sources, no library), `stale` (an input is newer) or `current`. Sources *and* headers count, because there is no dependency scanner: a timestamp check cannot know which translation units a header reaches, so the newest file wins whether or not anything includes it. It returns the paths and timestamps it decided from - `output`, `outputMtime`, `newestInput`, `newestInputMtime`, `sources`, `headers`, `bytes` - so `script.status` can show the reasoning rather than a verdict.
- **`buildScripts` can be told that up to date is good enough.** A third argument, `{ifStale: true}`, resolves to `{ok: true, skipped: true, output, durationMs: 0}` when the library is `current`: the command still names a loadable library, and no compiler is spawned, so a missing compiler is not an error for a project that has nothing to compile. Everything else - `noSources`, a real compile, compiler diagnostics, a launch failure - reports exactly as before, and the callers that want a compile still get one.
- **The editor had three entry points and only one of them used it.** Opening a project now runs `syncScripts()`: `current` loads the library as it stands, `missing` and `stale` build first, and `nosources` does nothing. **Ctrl+B** and the save of a `.cpp` build only when something changed, while **Rebuild Scripts** always invokes the compiler - so the automatic paths stop paying for a compile that cannot produce a different library, and the deliberate one still can.
- **A class the scene needs but the process does not have is named before the game starts.** Pressing Play checks every `Script` component's `class` against the loaded set and writes the missing names to the status bar and the console panel, so the report arrives at the moment the button is pressed instead of being buried in the runtime log one second later.
- **Tests.** The CLI grew 496 -> **517 checks** with a `cli: script staleness (script.status + script.build --ifStale)` section: a freshly built library is `current` and a build over it is a no-op that still reports loadable classes; backdating the library makes it `stale`; a header written afterwards becomes `newestInput` on its own; a stale library compiles and is `current` again; deleting the library reports `missing` and `--ifStale` builds it; and a project with no `Assets/Scripts` is `nosources` with `script.build` refusing with `not_found`. The editor calls the same two functions, and the editor's own path was exercised by hand over the DevTools protocol: a fresh `project-2d` with no library opened, the status bar reported the build it made on its own, the inspector's Script picker listed `Player2D`, and entering play logged `loaded 1 script class(es) from .../GameScripts.so` and `Player2D ready` with no `script class not found` anywhere in the console - before the change the same project could not resolve the class at all. The movement the missing load had been hiding was confirmed separately through the CLI on that project, where a transform can be read back: holding `ArrowRight` moved the player from `x` -5 to 1.775, and the script is the template's own.
- **Confirmed non-vacuous, five mutations.** Dropping headers from `collectHeaders` fails 1 CLI check; ignoring the `current` test (always skipping) fails 12; never skipping fails 1; inverting the timestamp comparison fails 5; and reporting a missing library as `current` fails 11. Each was applied, observed to fail and reverted.
- **Left open.** Staleness is timestamps, not dependencies: touching a file that no translation unit includes still forces a compile, and a build made by another tool at a newer timestamp passes as `current` even if it was compiled from different sources. `engine.version` is still baked into the library, so a library built by a previous engine reads as `current` and is then refused on load. And the editor has no UI test harness, so the console line and the status text are the hand-driven checks described above. Separately, a pre-existing rendering bug surfaced while looking at the same project in the editor: on the default Vulkan backend a 2D sprite that is not drawn 1:1 disagrees with the software rasteriser, which is why a `project-2d` scene view is garbled until the renderer is set to Software (`CAIRN_RENDER_BACKEND=software` renders the same frame correctly). It predates this change - no engine, addon or backend source was touched by 0.1.34 - and is recorded with its repro in `docs/roadmap.md`.

## [0.1.33] - 2026-10-18

### Tooling: a 2D panel, and the sheet model behind it
- **The 2D pipeline worked and could not be seen.** Slicing (0.1.25), frame animation (0.1.27), named clips (0.1.28), per-cell times (0.1.30), animation events (0.1.31) and clips naming their own texture (0.1.32) were all in the engine, all readable from the CLI, and all numbers: answering "which part of the sheet is this cell", "which cells does this clip play" or "how long is this one" meant putting the sprite in a scene, screenshotting it and reading fields back. Nothing drew the shape of the thing.
- **One model, two readers.** `editor/main/sheet.js` is the pure module both the panel and the CLI call: `resolveClip` (an entry's keys over the component's, including `texturePath`), `textureForClip`, `sheetGrid` (equal slices of the `uvRect` region in whole texels, the remainder going to the later cells), `clipTimeline` (`durations` counted from the clip's own `firstFrame`, falling back to `1 / fps` for a cell the table does not name), `frameAtPosition` (the play time as a cell, wrapping over the clip's reach, with a zero-second cell stalling the walk the way the engine's stepper does), `cellAtPoint` and `pixelGridLines`. The panel and `sprite.sheet` therefore cannot disagree about which cell is which - the same "one definition, two uses" the last three increments were built on.
- **The panel.** A `2D Panel` tab, opened from the Window menu or from a button on any `SpriteRenderer` / `SpriteAnimator` block, follows the selection: the sheet is drawn with its slicing (cyan) and the cells the clip plays (magenta), the current cell lit with the pivot marked, an optional texel grid on top, and the clip laid out underneath as a timeline whose boxes are as wide as each cell's own time - so "the first cell holds for half a second" is a wide box rather than a comment. Zoom, Fit, Cells and Pixel Grid control the canvas; the clip picker writes `clip`; clicking a cell or a timeline box and the prev/next buttons write `frame` and mark the scene dirty; while the game plays the panel follows the engine's own frame, so the scene view and the panel name the same cell.
- **The command.** `sprite.sheet` takes an entity instead of a file: it slices the same way and returns `{id, name, texture, textureSource, width, height, columns, rows, rect, region, cell, count, cells, clip, clips, frame}` plus a `preview` description. `--clip` picks a named clip, `--frame` the cell to mark, `--output` writes the preview PNG - the same marks the panel draws - and `--scale` zooms it, defaulting to `clamp(round(256 / max(w, h)), 1, 16)`. A missing entity, a sprite with no texture, an unreadable image and an out-of-range `--scale` are errors, not an empty table.
- **A value-only refresh reads what is there now.** The inspector's `entity-edited` refresh used to read the snapshot captured when the block was built, so a `frame` the panel had just written did not show up in its own row. Each refresh now reads the current value back from the engine, with a single scene tree shared across the rows of one pass, so the panel and the inspector agree by construction rather than by luck.
- **Tests.** `test/sheet.js` (new, **79 checks**) pins the whole-grid remainder, region clamping, clip ranges, per-cell times, the playhead (including the wrap and the zero-second stall), the texel hit test and the grid lines. The CLI grew 455 -> **496 checks** with a `cli: 2D panel (sheet slicing and the frame timeline)` section that slices a real project, reads the clip's cells and times, and checks the preview PNG's marks and zoom by pixel. The panel has no committed test - the editor has no UI test harness - so it was exercised by hand against a running editor over the DevTools protocol: `window.__cairnApp.open2D` opens it, and clicking a cell and a timeline box, wrapping with prev/next, switching clips, zoom and fit and the pixel grid were all driven the way a person drives them, with the frame number agreeing between the panel and the inspector and no exceptions in the renderer process.
- **Confirmed non-vacuous, nineteen mutations.** On `editor/main/sheet.js`: ignoring the `uvRect`, flooring instead of rounding an edge, reading a time by grid cell instead of clip position, letting a non-positive duration through, dropping the `-1` end frame, dropping the first-frame clamp, not wrapping a looping clip, dropping the zero-second stall, taking the far edge in the hit test, ignoring the texel grid's stride, not type-checking an entry's field, always using the sprite's texture, and not clamping a region to the sheet - **each fails 1 to 3 model checks**. On `sprite.sheet`: boxing the current cell instead of the clip's, not clamping `--frame`, ignoring `--scale`, losing `textureSource`, ignoring the sprite's `uvRect`, and not lighting the current cell - **each fails 1 to 2 CLI checks**. Each was applied, observed to fail and reverted.
- **Left open.** The panel looks and locates but does not edit: slicing lines cannot be dragged into an uneven grid and a timeline box cannot be stretched to change a cell's time. Transitions still hard-cut, so there is no weight for the panel to draw. There is no atlas asset between the texture and the entity - no per-cell names, no dragging a cell out of the sheet into a scene. And `image.draw.line` is broken at its default brush width: `strokeLine` stamps discs of radius `width / 2` and `stampDisc` drops every pixel at `d > r`, so a radius of 0.5 paints nothing on an integer-coordinate line and a 45° line comes out dotted and misses its own end (`--brush 3` is fine). ## [0.1.31] - 2026-10-18

### Rendering quality: animation events
- **An animation could not say anything part-way through.** A wind-up and a strike are one clip with a moment between them - the window opens, a hitbox should be live, the step has landed - and there was no way to name that moment: a script watching `frame` was guessing at the tick the frame changed, and a machine driven by parameters had nothing to drive it from inside the clip. `durations` (0.1.30) had just made the moment itself precise, and the moment was still unannounced.
- **`events` is a table on the clip**: `[{"at", "set"}]`, fired when the cell `at` names is entered, writing the object `set` into the parameters. `at` counts the clip's own cells from its first, so `{"at": 1}` is that clip's second cell wherever its range sits; `-1` is its last cell and anything out of range is clamped the way a frame is. `set` is the same bag `transitions` reads, so a clip can open the window its own state machine waits on, and the values are whatever was given - truth, a number, even a string. The key is on the component and on a clip entry with the same rule as `durations`: the entry's own array wins, `[]` clears the component's.
- **Entering a cell is the only thing that fires an event.** The clip's first cell fires when the clip is entered - starting play, writing `clip`, or a transition entering the state, because `Restart()` is what entering means here - and every following cell fires as the frame steps into it, one cell at a time, so a long `dt` fires each cell it passes in table order and the last write of the tick is the one left in the parameter. A looping clip fires them again on every pass. Nothing looks at a clock, so the same ticks write the same values in the same order; an entry with no `at`, no `set`, or an `at` that is not a number is skipped rather than guessed at.
- **Reading an event back is reading a parameter.** There is no queue to drain and no callback to wire: `anim->Param("landed")` from a script, `component.get` from the CLI, and a fired event leaves no trace beyond the values it wrote. A trigger is spent by the transition it fires, and the entered state's events run first, so an event that names the trigger which just fired is spent with it instead of re-arming the machine every tick - a subtlety the tests now pin, because the alternative is a table that walks a state per tick with no input at all.

## [0.1.29] - 2026-10-18

### Rendering quality: animation parameters and transitions
- **Clips were data, not behaviour.** 0.1.28 named a character's animations and made them switchable by name, but nothing decided *when* to switch: "walk while moving, attack when it is pressed, back to idle when the attack ends" had to be a script rewriting `clip` every tick, with the sequencing - the part the animation is - living outside the component, invisible to a scene file, a batch or a test. Play mode already had a clock and a per-state frame cursor; what was missing was a way to write the decision down.
- **`SpriteAnimator.params` are the values the animator reads.** One structured object, e.g. `{"moving": true, "speed": 2.5, "attack": false}`, written by a script or by `component.setProps` and stored, serialized and handed back like any other reflected field. There are no declared types: `is` reads a value as a bool, `gt` and `lt` as a number, so a bool that is compared numerically reads as 0 or 1 rather than raising - the same forgiving rule the clip table uses for a missing key.
- **`SpriteAnimator.transitions` is the table, evaluated in order.** Each entry is `{"from", "to", "when", "waitForExit"}`: `from` is the state it applies to or `"*"` for any state (and the default, so `{"to": "attack", "when": [...]}` fires from anywhere), `to` names the clip to enter, `when` is one condition or a list of conditions that all have to hold, and `waitForExit` holds the transition until the state's clip has played through once. The first entry that matches wins, which makes table order the priority and the whole machine a deterministic function of (state, parameters, elapsed time) - the same parameters over the same ticks always replay the same frames, which is what lets a batch render one frame of a state.
- **A condition is `{"param", "op", "value"}`.** `is` and `not` compare as a bool (a bare `is` means "is true", so `{"param": "moving", "op": "is"}` needs no `value`), `gt` and `lt` compare as a number, and `trigger` is a one-shot event. A parameter that is not set holds nothing - a transition on a value the animator does not have is inert rather than taken as false - and an `op` that does not exist never matches, so a half-edited table degrades the way a half-edited clip table does.
- **A trigger is spent by the transition it fires.** `EvaluateTransitions` clears every `trigger` condition of the entry it runs, so a press is consumed exactly once and the machine does not re-fire on the next tick: `params.attack` reads `false` afterwards, which is also what makes the state observable in a `component.get`. A self-transition (`"from"` and `"to"` the same clip) is allowed and replays the state - entering a state restarts its frame and its clock - which is how a trigger re-plays a one-shot clip.
- **The exit time is measured, not guessed.** `ClipLength()` is the state's cell count over its own rate, and `Finished()` is "the state has been playing for at least that long", read from a per-state clock reset when the state is entered. A one-cell state has a length too, so a one-frame `hurt` can still be held for its own duration; a state whose clip has no frame rate has no length and therefore never finishes, which is the only way `waitForExit` can fail to fire. This is Unity's exit time reduced to the one bit the increment needs; a normalized fraction is a later addition.
- **Order within a tick, and where the machine runs.** The engine's `animation` pass advances the frame first (`AdvanceAnimation`) and then evaluates the table (`EvaluateTransitions`), so a transition sees the tick it belongs to - the exit time is the clip that just finished, not the one before - and the state it enters is what the frame being rendered shows: the first cell of the new clip, before any tick of it has run. `clip` remains a plain field, so writing it by hand is still a manual override of the machine, and `DrawnCell` (0.1.28) already draws a switched-to clip's first cell without a tick in between.
- **Tests.** `TestSpriteTransitions` (new) reuses the four-quadrant sheet - one authored colour per cell - and drives both backends, reading every state back as the colour on screen rather than as a field, so a state is pinned by what is drawn. Three blocks. The first runs the whole loop: `idle` holds while `moving` is false; `moving = true` moves it to `walk` and the next step shows the walk's second cell; `moving = false` with `speed = 1` is blocked, which is one of the two conditions holding and not enough; `speed = 0.1` lets it back to idle, which is both holding; a trigger then moves it from idle to `attack` and is read back as spent; and the exit time holds `attack` for its clip length and then releases it to idle. The second pins the table's semantics: with two entries that both match, the earlier one is the transition that runs (checked through the return value and the drawn cell), the second is next in line when the first does not match, nothing fires when the value is below both thresholds, `lt` fires and then stops firing once the value crosses it, a stray non-object entry is skipped and an unknown `op` never matches. The third covers the pieces the first two do not: a transition with no condition and no exit time fires on the first tick, a self-transition on a trigger replays the clip from its first cell (the drawn cell moves backwards, which a plain "no state change" implementation cannot produce), and writing `clip` is still a manual override. The CLI suite grew 372 -> **403 checks** with a `cli: sprite animation states (parameters drive the clips)` section: one batch builds a sheet, adds an animator with three clips, a parameter bag and a four-entry table, and reads eight `runtime.step` / `render.screenshot` pairs with `image.pixel` - start, the parameter-driven move, the state's own frames, the blocked transition, the released one, the trigger, the exit time holding, and the exit time releasing - then requires `component.get` to return the spent trigger, the untouched parameters and the table as they went in, and `component.schema` to report `params` and `transitions` as `json` props.
- **Confirmed non-vacuous, six mutations.** Not running the machine in the engine's update pass fails **18 engine checks** and 6 CLI checks; ignoring `waitForExit` fails **2 engine checks** (the state that should be held) and 1 CLI check; not consuming the trigger fails **6 engine checks** (the trigger keeps firing) and 3 CLI checks; treating a condition list as "any of them" instead of "all of them" fails **4 engine checks** (the blocked-then-released pair, both backends); treating an unknown `op` as a match fails **2 engine checks**; and evaluating the table last-entry-first instead of first-entry-first fails **4 engine checks** (the priority checks). Each was applied, built, observed to fail, and reverted.
- **Left open.** A transition has one condition semantics and no interpolation: there are no blend trees, no cross-fades, no transition durations and no `anyState` exit-time offsets, so a state change is a cut from one clip to another. Conditions cannot compare two parameters, and `params` is replaced wholesale by a `component.setProps` - there is no per-parameter merge, so a batch writes the whole bag. There is still no per-frame duration, no animation event, and a clip cannot name a different texture.

## [0.1.26] - 2026-10-18

### Rendering quality: sprite culling measures the sprite
- **The 2D cull tested a bound that had nothing to do with the sprite.** `float w = sp->pixelsPerUnit * 0.5f`, symmetric about the entity: a number proportional to the pixels-per-unit, blind to the texture, to the atlas rect and to the pivot. It was wrong in both directions. A sprite whose entity sat outside the view but whose pixels covered it - a pixels-per-unit below one, which is how a background or parallax layer is set up - was culled away and left the screen empty; and a genuinely off-screen sprite at the default 100 px/unit was credited with a 50-unit bound, so it was submitted and clipped on every frame instead of dropped.
- **The bound is now the quad, from one shared definition.** `SpriteLocalExtent` turns a `SpriteRenderer` and the texture's texel size into the quad's local extent - the atlas rect's texels over the pixels-per-unit, offset by the pivot, mirrored by `flipX`/`flipY` - and the frustum test and the vertex generation both call it, so they cannot drift apart again. The texture is resolved once, in the gather loop, and the same `shared_ptr` is handed to the draw, so the size that decided the cull is the size that gets built.
- **`pixelsPerUnit` below one is honoured.** The size computation clamped it with `std::max(1.0f, ppu)`, which silently drew any sprite set below 1 px/unit at 1 px/unit: a layer meant to be twice its texel size came out at its texel size, and the documented `texturePixels / pixelsPerUnit` was not what the renderer did. The guard now only catches values of zero or less, which have no meaning; every positive value is used as written.
- **Tests.** `TestSpriteCullBounds` (new) covers four cases on both backends: an entity 50 units outside a 2-unit view whose 160-unit sprite covers it (drawn, `drawCalls2D == 1`, `frustumCulled == 0`); a 0.16-unit sprite 3 units out (dropped, `0`/`1`); and the same entity with `pivot = (0, 1)` versus `(0.5, 0.5)`, where the pivot alone decides whether the rect reaches the view. The CLI grew 316 -> **327 checks** with a `cli: sprite culling (the bound is the quad, not the ppu)` section: it draws the texture with `image.new`, renders one covering and one off-screen sprite in the same frame, reads `drawCalls2D` / `frustumCulled` from `render.screenshot` and checks three points of the frame with `image.pixel`.
- **Confirmed non-vacuous, both mutations.** Restoring the old `pixelsPerUnit * 0.5` bound fails **16 engine checks** (both backends x three cases x three assertions) and 3 CLI checks; restoring the `max(1.0f, ppu)` clamp fails 6 engine checks and 4 CLI checks. Each was built, observed to fail, and reverted.
- **Left open.** A sprite's texel size comes from the texture, so the gather has to resolve the texture before it can cull: an entirely off-screen sprite still loads it once (the LRU then holds it, though a budget eviction can make the next frame load it again). The shape this should take later is Unity's: the size is an import result in the asset database, and `AssetMeta::settings` is already a Json that can carry it. ## [0.1.25] - 2026-10-18

### Rendering quality: sprite atlases (uv rect and pivot)
- **Every sprite drew the whole texture, centred on its entity.** `SpriteRenderer` had no way to name a sub-rectangle, so one texture could only ever be one sprite: `image.stamp` could already assemble a sheet, but the sprite pass fed the whole thing through with hard-coded uvs (`{{0,1},{1,1},{1,0},{0,0}}`). "One image, many frames" - the prerequisite for 2D animation, and the shape AI-drawn art arrives in - was not expressible, and the drawn size was always the whole texture's texels over the pixels-per-unit, so a 4-frame strip rendered as one stretched strip.
- **`SpriteRenderer.uvRect` is a `Vec4` of `{x, y, w, h}` in normalized image coordinates** - `(x, y)` is the rectangle's top-left corner, so the default `{0, 0, 1, 1}` is the whole texture and frame `(col, row)` of a `cols`x`rows` sheet is `{col / cols, row / rows, 1 / cols, 1 / rows}`. Rows count from the top, which is the order `image.stamp` lays frames out in and the order every other image coordinate in the engine uses (0.1.23 settled image-top = world-top). The drawn size follows the rect (`frameTexels / pixelsPerUnit`), and the quad's uvs are the rect's four corners - the 0.1.23 fix generalized: the two *top* corners still take the rect's low `v`, so an atlas cannot silently reintroduce the mirroring that fix removed.
- **`pivot` is a `Vec2` of the sprite's own coordinates** - the point that lands on the entity's position, in the same image coordinates as `uvRect`: `(0, 0)` top-left, `(1, 1)` bottom-right. The default `(0.5f, 0.5f)` reproduces the old centre-anchored behaviour exactly, so nothing that already existed moves; `(0.5f, 1.0f)` stands a frame on its feet. `flipX` / `flipY` now mirror the extents *about the pivot* rather than about the centre, which is what makes flipping a footed character keep its feet on the ground. Both fields are declared in `SpriteRendererDefs`, so they round-trip through scene JSON, appear in `component.add` / `component.setProps`, in `component.schema` and in the editor inspector without further wiring.
- **Tests.** `TestSpriteAtlas` (new) writes a 16x16 four-quadrant BMP with its own reading-order writer (`WriteTestBmpSheet`) and drives both backends through an orthographic game camera. It renders each of the four rects and asserts the frame that was named is the frame that appears (each quadrant has its own colour, so an ignored rect draws a different one); it asserts the drawn size is the *frame's* - a whole-sheet sprite would cover the corners that must stay background; and it renders a sprite with `pivot = (0, 1)` and holds it to the view's top-right quadrant, which pins both pivot axes and would catch either sign. White ambient and `tonemap = 0` in that scene make a texel's authored colour reach the frame unchanged, so these are exact-colour checks rather than "not black". The CLI suite grew 298 -> **316 checks** with a `cli: sprite atlas (uv rect + pivot)` section: it draws a 32x32 sheet with four `image.draw.rect` calls, renders one named frame at `pixelsPerUnit 16` and reads the frame and the background back with `image.pixel`, then tiles four sprites - one per rect, each pinned by `pivot = (0, 1)` - over the view and checks the colour in each screen quadrant.
- **Confirmed non-vacuous by two mutations.** Hard-coding the uv rect (and therefore the size) to the whole texture fails **16 engine checks** (both backends x four rects x the size check) and 3 CLI checks; hard-coding the pivot to the centre fails **4 engine checks** (both backends x pivot assertion) and 3 CLI checks. Each mutation was applied, built, observed to fail, and reverted - the pivot mutation was reverted and rebuilt before the uv-rect one was tried, so their failures could be attributed.

## [0.1.24] - 2026-10-18

### Build: a multi-config generator no longer hides the engine library
- **A successful CMake build could still leave `npm run build` failing with "engine library output not found".** Visual Studio is the default CMake generator on Windows and it is a *multi-config* generator: it ignores `CMAKE_BUILD_TYPE`, appends a per-configuration subdirectory to every output directory, and builds `Debug` unless `cmake --build` is told otherwise. The DLL and its import library therefore landed in `engine/build/Debug/`, while the staging step looked only in `engine/build/` - the compiler had done its job and the failure was in the staging step. Removing the per-configuration directories from the search fails 4 of them.
- **A job that can actually run guards the path the Windows job depends on.** The new `multi-config` job configures `engine/build` with `-G "Ninja Multi-Config"` on Linux and then runs the ordinary `npm run build`, the staging test, `npm run test:engine` and `engine.version` - the last one loads the native addon, which proves the staged library is linkable, not merely present.
- **Left open.** The MSVC toolchain itself still cannot be exercised locally, so the `windows` job keeps `continue-on-error: true` and the limitation stays in `docs/roadmap.md`. What is fixed is everything after CMake: where the artifacts are written and how they are found, staged and loaded.

## [0.1.23] - 2026-10-17

### Rendering quality: 2D up is up
- **Every sprite and every word rendered vertically mirrored.** Image space is y-down throughout the engine: `image.draw.rect` puts `y = 0` at the top, a written PNG's row 0 is the top, `image.pixel` reads `y` down from the top, and a loaded texture's row 0 is `v = 0`. The 2D quad's corner order, however, is `{bottom-left, bottom-right, top-right, top-left}`, and both call sites handed `v = 0` to the **bottom** two corners - so the image's top row was drawn at the bottom of the sprite. `flipY` was never the culprit: it negates the quad's height, so it simply mirrored the already-mirrored picture (and it still means what it says, "turn the picture over"). The fix is two uv arrays: the sprite's `{0,0},{1,0},{1,1},{0,1}` becomes `{0,1},{1,1},{1,0},{0,0}` so the *top* corners take `v = 0`, and the glyph quad's bottom corners take `g.v + g.h` instead of its top corners. `AppendQuad`'s contract is now spelled out where it is defined: `uv[k]` pairs with `world[k]`, and callers give the **top** corners the low `v`.
- **The normal-map green convention was settled on the way, because the orientation fix is not well defined without it.** `image.normalMap` encodes slopes in image space (`ny = -dh/d(image y)`, so a green channel below 0.5 means the surface normal leans towards the **top of the image**). `sprite.frag` and the software sprite path both read the green channel negated, which was in fact correct for the flipped orientation and *is* correct for the fixed one: repairing the quad turns "image top" into "world top", so the negation lines the 2D lighting up with the albedo instead of against it. **No shader change was needed** - the two changes compose - and the convention is now pinned rather than implied: `TestSpriteNormalOrientation` renders a white sprite twice, with two normal maps that differ only in the green channel (leaning to the image top versus the image bottom), under a point light directly above it, and asserts the top-leaning map is brighter. ## [0.1.22] - 2026-10-17

### Rendering quality: 2D quads and pixel-perfect sampling
- **The software rasteriser drew half of every 2D quad.** The shared 2D vertex buffer is a triangle list: `AppendQuad` pushes **six** vertices per quad (`{0,1,2,0,2,3}`), and the GPU backend uploads the range verbatim and draws it as a triangle list, which is correct. The software path's `EmitQuadVerts` instead read the first **four** vertices as if they were the four corners and re-split them itself as `{0,1,2},{0,2,3}` - but the fourth stored vertex is `w0`, not `w3`, so the second triangle came out as `{w0,w2,w0}`, degenerate, and was dropped by the area test. The visible effect was that **every sprite and every glyph rendered as a single triangle**: a solid-colour texture filling a screen-sized quad came out as one half of the quad, and a four-quadrant sprite came out diagonally sliced. The fix splits the shared block into **triples** (`for (v = 0; v + 3 <= count; v += 3)`), so the software path and the GPU path consume the same triangle list. Text items are triangle lists too, so glyphs are repaired by the same change.
- **`pixelPerfect` sprites were sampled through a linear, mipmapped sampler on the GPU.** The software reference forces `Filter::Nearest` and lod 0 for `pixelPerfect`, and `pixelPerfect` is what disables the software path's anti-aliasing - but `engine/src/backend_vulkan.cpp` mapped `pixelPerfect` to `linearClamp`, which is created with `VK_FILTER_LINEAR` (the only nearest sampler, `nearestClamp`, was reserved for shadow taps). So on the default GPU backend AI-drawn pixel art was bilinearly filtered *and* free to read from the mip chain, and the two backends disagreed picture-for-picture - the exact situation rule 3 of the roadmap ("any picture difference between the two paths is a GPU-side bug") exists to forbid. The fix adds a dedicated `pixelClamp` sampler - `VK_FILTER_NEAREST`, `CLAMP_TO_EDGE`, `mipmapMode NEAREST`, and **`maxLod 0`** so the base level is the only one that can ever be selected - and uses it for both the albedo and the normal-map slot of a pixel-perfect 2D item (a `maxLod` of 16 was added as an explicit argument to `makeSampler` so the three existing samplers are unchanged).
- **The two backends now agree on the pixels, not just on the vibe.** The existing cross-backend net (`TestRenderBackendsAgree`) only compared lit-pixel *counts* with a 2x tolerance on an editor camera, so neither bug was ever in its blast radius. Rendering a 64x64 four-quadrant sprite through a game camera used to differ in **2500 of 4096 pixels** with a full spread of interpolated colours between the four quadrants; after both fixes the frames are **identical (0/4096)** and contain exactly the four expected flat colours.
- **Surfaces:** `Renderer::EmitQuadVerts` in `engine/src/renderer.cpp` now takes `(const Vertex2D*, uint32_t count, const MaterialGpu&)` and is called once per 2D item with the item's whole range (the per-6-vertex loop and its `v + 6 > count` guard are gone). `engine/src/backend_vulkan.cpp` gains the `pixelClamp` member, the `maxLod` parameter on the `makeSampler` lambda, the pixel-perfect slot selection, and the sampler in the destroy list. No new CLI commands, so `docs/cli.md` is unchanged.
- **Tests:** `TestSpriteQuality` (new) builds a 16x16 one-texel red/blue checker BMP, drives a forced software engine and then a forced Vulkan engine through an orthographic game camera with the sprite overfilling the view (`pixelsPerUnit 6`, `orthoSize 2`, MSAA 1), and asserts two invariants: **all four quadrants of the quad are non-background** (a dropped triangle leaves the upper-left quadrant as the black clear colour) and the sprite's interior holds **at most four distinct colours** (nearest sampling yields two lit colours; a linear sampler blends red and blue into purples all along every texel edge). The CLI suite grew 276 -> **287 checks** with a `cli: sprite 2D rendering quality` section that draws the four-quadrant sprite with `image.*`, renders it through `SpriteRenderer` on the software backend, and reads the PNG back with `image.pixel` and `image.palette --list`: the full frame must be exactly four colours and must not contain the background black.
- **Confirmed non-vacuous by two mutations (engine) and one (CLI).** Restoring the old `{0,1,2},{0,2,3}` four-corner split fails the quadrant-coverage check in `TestSpriteQuality` and two CLI checks (`the fourth quadrant is the lit white corner`, `the sprite covers its whole quad, both triangles`); pointing `pixelPerfect` back at `linearClamp` fails the four-colour check in `TestSpriteQuality`. The mutations were applied, built, observed to fail, and reverted.
- **Documentation and backlog.** The 2D renderer had no documentation at all: no test touched sprite pixels and no hand-written doc mentioned the component (the bundled `project-2d` template did use `SpriteRenderer`/`TextRenderer`, but nothing rendered or documented them - see 0.1.23). `docs/roadmap.md` gains a 0.2 layer ("渲染质量与 2D 管线") with what 0.1.22 fixed and a prioritised candidate list for the next 2D increments - **sprite/text vertical orientation** (the image tools are y-down, `image.draw.rect` at y=0 lands at the top of the PNG, but the 2D quad maps texture row 0 to the *bottom* of the sprite, so sprites and text render upside down; `flipY` flips geometry, not the texture-v relationship; fixing it means settling the normal-map green convention at the same time), **sprite atlas / uv-rect / pivot** (`image.stamp` can already assemble a sheet, but `SpriteRenderer`'s uvs are hard-coded to the whole texture, so one-image-many-frames cannot be drawn), and **the sprite cull bounds** (`float w = sp->pixelsPerUnit * 0.5f` instead of `texturePixels / pixelsPerUnit`, which is far too large for `ppu >= 1` and wrongly tiny - culling visible sprites - for `ppu < 1`). The orientation limitation is also recorded under 已知限制.

### Tooling: the closed loop, written down
- **The drawing track's last step was documentation, so the documentation is executable.** [`docs/drawing.md`](docs/drawing.md) is a walkthrough of the whole loop - `draw -> look -> fix -> confirm` - against the two surfaces that make it possible without a visual model: `image.preview` (the picture as text, one character per pixel at `--scale 1`) and `image.info` (bounds, coverage, mirror symmetry with mismatch counts, top colours, edge clipping; `--spans` for per-row/per-column extents). The chapter cannot drift from the implementation. `README.md` and `README.zh-CN.md` point at it from the docs table. CLI suite 252 -> **276 checks**.

### Fix: painting with opacity over transparency
- **`blendPixel` blended a semi-transparent stroke against a transparent pixel's RGB as `src * a`.** If the destination had no alpha there is nothing to interpolate towards, but the old formula still multiplied the source by its own opacity and stored that as the colour: a 50% white fill on an empty layer was stored as **grey at 50% alpha** rather than white at 50% alpha, and `composite()` then darkened it a second time - the fill composited to **25% grey** over an opaque black backdrop instead of 50%. It also meant the same highlight looked *duller* on its own layer (`#ddca8d`) than drawn straight onto the body layer (`#fde9a4`), which is how writing Recipe 1 of the tutorial surfaced it.
- **The fix weights the colour by the destination's own alpha**: `(src * a + dst * dstA * (1 - a)) / max(dstA, a)`, straight-alpha storage, which is exactly the old `src * a + dst * (1 - a)` whenever the destination is opaque. So none of the existing drawing behaviour changes (all 252 prior checks pass unchanged, including the exact-mirror-symmetry and outline tests), the alpha channel still uses `max()` rather than source-over so a repeated stroke or a mirrored draw cannot build up coverage, and painting onto transparency or onto a semi-transparent region now stores what the artist asked for.
- **Tests:** six new checks in `cli: opacity over transparency` - a 50% fill on transparency stores `#ffffff` at alpha 128, a repeated stroke does not build up, 50% white over opaque black composites to `#808080`, an opaque stroke still covers a semi-transparent one, and the blend over an opaque layer is unchanged. Reverting `blendPixel` to the old formula fails four of them (verified).

## [0.1.20] - 2026-10-17

### Physics: overlap box and shape casts
- **The query surface stops being a single ray.** `Physics::Raycast` and `OverlapSphere` answered "what is along this line" and "what is inside this ball"; there was no way to ask "what is inside this box" or "what will this sphere hit first if it moves" - the two questions a script asks constantly (is the ground under me, is there room to land, will I clip that corner). `physics.overlapBox`, `physics.sphereCast` and `physics.boxCast` (engine: `Physics::OverlapBox`, `Physics::SphereCast`, `Physics::BoxCast`) close that gap.
- **An overlap box reuses the solver's own separation, so it is exact rather than a bounding-box guess.** `PhysicsOverlapBox` builds a `Box3` shape and asks `ShapeSeparation` - the same signed-separation path the step resolves and CCD sweeps with - so a box query is exact against a sphere, a capsule, another box *and* mesh triangles (the last two would silently degrade to an AABB test if this had been written as its own comparison). The test pins the difference: a query box that clips a radius-0.75 sphere's bounding-box corner but stays 0.86 from its centre must report nothing, and an AABB-based version reports the sphere.
- **A shape cast is conservative advancement, not a sampled sweep.** The casts reuse the walk CCD already does - at the current pose take the separation to the obstacle, step forward by `separation / closing speed`, repeat, so a hit is a real time of impact rather than the first sample to be inside. The one deliberate difference is that the cast ignores the layer matrix: the layer matrix is a property of the *step*, not of a *query*, and `Raycast` has always ignored it too. `point` is the contact point on the swept shape's own surface (the AABB support point along the contact normal for a box, the centre minus radius for a sphere), which at the moment of contact lies on the obstacle's surface as well. A cast that starts already overlapping reports distance 0 - "something is already here" is more useful than a miss.
- **The surface decides, and the tests hold the cast to that.** A ray down `x = 0.6` beside a unit crate slips past it and reaches the floor at 9.5; a radius-0.5 sphere cast from the same centre stops on the crate's top-right *edge* at `10 - 3.5 - sqrt(0.25 - 0.01) = 6.01` with the normal `(0.2, 0.98, 0)` and the contact point exactly on the crate's corner `(0.5, 3.5, 0)`. A 1x1x1 box cast at `x = 0.9` - whose left face clips the crate - stops on the crate top at 6.0 while a box clear of it in `x` drops to the floor at 9.0. Keeping the radius in the sphere cast, keeping the AABB test in the overlap box, or degenerating the box cast to a ray each fail those checks (verified).
- **One convention fixed on the way.** `ShapeSeparation`'s box/box branch oriented its normal by `min` vs `max` (as `Collide` used to), which is ambiguous exactly at the touch boundary - both comparisons are false there, so the sign was arbitrary. It now orients by centre, which is what `Collide` already does for boxes; separated behaviour is unchanged, and a cast that stops just short now reports a normal pointing out of the obstacle instead of into it.

## [0.1.19] - 2026-10-17

### Physics: mesh collider
- **`MeshCollider` takes its collision geometry from a triangle mesh**, so a scene can finally be more than boxes and spheres: a ramp, a room, a corridor, a cave, a wrecked ship hull - the level geometry a game actually stands on and the one shape family the primitives cannot approximate. Unity calls this the non-convex MeshCollider, and this is the same thing: a project-relative `.obj` (resolved exactly like `MeshRenderer::meshPath`) plus `isTrigger`.
- **It is a triangle soup, so it is static/kinematic only.** A non-convex soup has no well-defined response for a body the solver has to push - there is no single contact normal for a concave surface - which is exactly why Unity forbids a non-convex MeshCollider on a non-kinematic RigidBody. Rather than adding a `convex` flag that would be stored and ignored, the flag is simply absent: a `MeshCollider` on a non-kinematic body is **dropped** and reported once in the engine log ("MeshCollider on 'X' is ignored: a non-convex mesh is static-only"), and the body still integrates and falls. Dropping the whole body from the step would have been worse - a component that freezes its entity reads as a bug, a component that says what it did and lets the entity move reads as a rule. Two mesh colliders do not interact at all.
- **Each primitive gets its exact test, not an approximation.** Sphere vs triangle is the closest point on the triangle (Ericson's region test) minus the radius. Capsule vs triangle is the closest pair between a segment and a triangle, built from a candidate set - both segment endpoints against the triangle, each of the three triangle edges against the segment, and the segment's foot on the triangle's plane - which is complete, and since every candidate is a real point pair the smallest is the true distance and the reported normal comes from the actual closest pair (so a capsule resting across a triangle edge is pushed out along that edge, not along the face). Box vs triangle is the 13-axis separating-axis test (3 box axes, the face normal, 9 edge cross products); the **largest** gap over those axes is the separation and the axis carrying it is the contact normal, which is the same convention the AABB/AABB branch has always used, so separation and penetration are one code path: positive gap means apart, negative means overlapping, and the deepest triangle over the soup wins.
- **The prune is a distance, not a bounding-box hit - and that distinction is the difference between working CCD and a tunnel.** The first cut skipped any triangle whose AABB did not touch the other shape's AABB. That is a valid reject for an *overlap* test, but not for a *separation*: a triangle 7.8 units away is still the closest surface, so the function reported "no interaction" (1e30) for a body approaching a wall, `CcdTimeOfImpact` read that as "nothing ahead", and a 600 u/s bullet sailed straight through a zero-thickness mesh. The prune is now `BoxGapSquared(triangle box, shape box) > best * best` - a triangle whose surrounding boxes are already farther apart than the best separation found so far cannot be closer, so the minimum stays exact and the sweep keeps its distance. This is a real bug the tests caught (they were written before it was fixed, and failed), not a hypothetical.
- **CCD and the character controller come free.** Both only ever asked `ShapeSeparation`, so giving the mesh a branch there is all it took: a `Continuous` body sweeps against a mesh wall and stops on the surface, and a `CharacterController` stands on a mesh floor - no second code path, no separate mesh sweep.
- **Raycasts hit the triangles, not the box around them.** `RayShape` runs Möller-Trumbore per triangle in the mesh's **local** space (the inverse world matrix transforms the ray, so no triangle is ever moved) and converts the local parameter back to a world distance by the same factor that scaled the local direction - so a scaled collider still reports a correct distance. The hit normal is flipped to face the incoming ray, so a shot through the back of a wall still reports a usable normal. `Physics::OverlapSphere` is likewise exact against the triangles rather than the bounding box, and a single triangle therefore reports a hit on the half of its bounding box it occupies and a miss on the empty half.
- **Triangles are stored in local space with the transform that puts them in the world**, so a rotated, scaled, parented or kinematic collider needs no per-triangle rebuild (and a kinematic platform carries its mesh collider with it, exactly as it carries a BoxCollider). A roughly uniform scale is assumed for the ray's normal, the same assumption the sphere and capsule colliders already make with `WorldMaxScale`.
- **Surfaces:** `MeshCollider` in `engine/include/cairn/scripting.h` (forward declaration, `ComponentTypeId::MeshCollider` appended with an "Added in 0.1.19" comment, `CAIRN_COMPONENT_TYPE`, the class with `meshPath` / `isTrigger`), its reflection table in `engine/src/components.cpp` (so the inspector, `component.schema` and `component.add` all see it), the factory in `engine/src/scene.cpp`, `MeshCollider` in `cli/lib/constants.js`, `comp.meshCollider` in `i18n/en.js` and `i18n/zh-CN.js`, and the inspector's add-menu and title maps in `editor/renderer/src/ui/inspector.js`. `engine/src/physics.cpp` gains `Shape::Mesh3` (a `shared_ptr<Mesh>` plus the mesh's world matrix and its inverse), `MeshTriangle` / `ClosestOnTriangle` / `ClosestSegmentTriangle` / `SphereTriangleSeparation` / `CapsuleTriangleSeparation` / `BoxTriangleSeparation` / `MeshSeparation`, the mesh branch in `Collide` and `ShapeSeparation`, the mesh branch in `RayShape`, the exact mesh path in `PhysicsOverlapSphere`, and the gather that drops a mesh on a dynamic body. `npm run docs:cli` regenerated `docs/cli.md` (still 137 commands - a component type, not a command).

## [0.1.18] - 2026-10-17

### Tooling: agent-facing drawing — textures
- **Three primitives that make a *texture* instead of filling a shape with one colour.** 0.1.14 and 0.1.15 gave an agent a preview/statistics surface, shapes, mirrors, transforms and composition - but every one of them paints a solid: there was no way to make clouds, a dirt patch, a tile of grass, a sky, or a sprite reduced to a fixed palette, which is exactly what a texture is. `image.draw.noise`, `image.draw.gradient` and `image.palette` close that gap (the core is new code in `editor/main/imaging.js`, driven from `cli/commands/image.js`).
- **Noise is a pure function of its seed.** `image.draw.noise --kind value|white|fractal --seed N` makes the whole field a function of `(seed, x, y)` - an integer hash, nothing reaching `Math.random`, no time, no hidden state - so the same command always paints the same pixels and two revisions of a generator can be diffed. `value` is smooth blobs, `white` is per-pixel grain, and `fractal` sums octaves (`--octaves --lacunarity --gain`) over a lattice whose cell size is `--cell`. `--from`/`--to` are the two ends of the colour ramp and the optional `--x/--y/--width/--height` region limits the fill (whole canvas by default).
- **`--tile` makes a seamless tile, and a test proves it.** With `--tile` each octave's lattice is snapped to an *integer* number of cells across the canvas, so the field is exactly periodic in the canvas size and the two edge columns meet like any two neighbouring columns. The test measures exactly that: the difference across the seam is no larger than the largest difference between adjacent columns *inside* the image, while without `--tile` the edges are unrelated (98 levels against 3 at seed 4). "Seamless" only counts as delivered if it can be measured.
- **Gradients.** `image.draw.gradient --kind linear` runs along an axis through the canvas centre whose length is the box's extent along it, so the two opposite corners land on 0 and 1 whatever the angle (the CSS convention): `--angle 90` is top to bottom, `--angle 0` left to right, or give `--x1/--y1/--x2/--y2` for explicit endpoints. `--kind radial` runs from `--cx/--cy` out to `--radius` (default: the canvas centre and half the smaller side). Both take the same ramp / region / opacity arguments as the noise.
- **Ramps composite source-over, not brush-style.** `compositePixel` does the straight-alpha source-over the composite and stamp paths use, so `--opacity 0.5` over a 50% pixel really blends to 75% instead of taking the larger alpha the brush path does (and leaving a hole). The brush semantics are untouched - this is a new primitive, not a change to an old one.
- **`image.palette` quantizes** with a median cut (`--colors`, 1-256) or snaps the layer onto a palette you give (`--palette "#1a1c2c,#5d275d,…"`), with `--dither none|ordered|floyd` to break up the bands. The histogram is collapsed to *distinct colours with their counts* before the cut, so a flat sprite comes back as exactly its own colours with no duplicate entries; boxes split along the channel they span widest, at the population-weighted median. Floyd-Steinberg diffuses the error to the right and down, ordered adds a 4x4 Bayer threshold scaled to the palette's own mean step; both use one threshold/error per pixel on all three channels, so the dither does not shift the hue. Fully transparent pixels are left alone and semi-transparent ones keep their alpha.
- **`--list` is the self-check half of the increment.** It changes nothing and reports the palette plus how many pixels land on each entry (exact counts for a flat image); with an explicit `--palette` it reports how those pixels would be distributed. So the "draw → check → fix" loop is no longer only about shape (`image.preview` / `image.info`) - an agent can read what colours its sprite is actually made of without a visual model.
- **Surfaces:** `editor/main/imaging.js` gained `noiseField`, `drawNoise`, `drawGradient`, `regionBounds`, `colourHistogram`, `medianCutPalette`, `paletteFromImage`, `quantizeLayer` and `paletteCounts` (all zero-dependency and pure, keeping the codec/core rule); `cli/commands/image.js` gained the three commands and a `--palette` parser. ## [0.1.17] - 2026-10-17

### Scene: prefab per-property overrides
- **An instance now remembers how it differs from its asset.** 0.1.3 shipped prefabs as *template + link*: an instance was a copy with no memory of what it had changed, so an edit to the `.prefab` could not reach it without throwing the local changes away. An instance now carries an override record (`PrefabInstance::overrides`), the scene is saved with it, and **loading a scene pulls the asset back in for everything the instance did not change** - so editing a prefab reaches every instance that left the property alone, while a per-instance tweak survives the edit, the save and the reload. That is the Unity model, and it is the gap the roadmap listed as the top scene-level one.
- **The record is a plain diff of two serialized subtrees**, computed when the scene is saved, by `prefab.overrides` and at `prefab.apply` - not a set of setters that every code path would have to be routed through. The consequence is that anything that changes the entity shows up: a colour set through the CLI, a `Transform` moved by physics, a script property written from C++, a component disabled in the inspector. A property setter-based scheme would silently miss all of those.
- **Keys read like a path through the prefab.** The record is keyed by node path (`""` is the instance root, `"Lid"` a child, `"Body/Wheel"` deeper) and then by property: `@name` / `@active` / `@tag` / `@layer` for the entity's own fields, `MeshRenderer.albedoColor` for a component property, `MeshRenderer.@enabled` for a component's enabled flag, `Transform.position` and `Script.speed` for the two types with a shape of their own, and `@removedChildren` / `@removedComponents` for what the instance dropped. Nodes are matched **by name among siblings, in order** (so twin children line up), which is what keeps the record readable.
- **Numbers compare with a tolerance, and that is load-bearing.** The JSON writer prints ten significant digits (`%.10g`), so re-reading a file does not reproduce the exact `double` a `float` converts to - an exact compare would declare *every* float in the asset a difference the first time a scene was reloaded, and the record would be full of noise. A relative 1e-6 (absolute 1e-9 at zero) sits four orders of magnitude above that write error and three below any change an author makes by hand, so it separates "the file was read back" from "this was edited".
- **New commands.** `prefab.overrides --id` refreshes the instance and lists its differences one row per property (`{node, key, value}`), so an agent can read them without knowing the stored shape. `prefab.sync [--id]` re-pulls the assets (all instances when `--id` is omitted), which is what a scene load does automatically. `prefab.apply` now means what Unity means: record the local differences, re-pull the asset *keeping* them, then write the instance back as the new asset - so applying can no longer resurrect a value the asset has since moved past, and its siblings follow immediately.
- **Removals are remembered per instance.** Deleting a component or a child on one copy is recorded (`@removedComponents` / `@removedChildren`) and a later sync does not resurrect it - without that, every load would undo the deletion. The asset keeps its own node: the record suppresses the template node for *that* instance only.
- **Legacy scenes keep their work.** A scene written before 0.1.17 has no record at all, and `overridesKnown` is false; the loader then treats the instance's own state as the record (recomputes the diff first) instead of letting the asset overwrite edits made in an older version. A fresh `prefab.instantiate` is the opposite case and is marked known with an empty record, because a new copy *is* the asset.
- **Surfaces:** `PrefabInstance` gained `overrides` / `overridesKnown` in `engine/include/cairn/scripting.h`; the new engine contract is `RefreshPrefabOverrides(id)` (id 0 = every instance), `PrefabOverrides(id)` and `SyncPrefabs(id)` in `engine/include/cairn/engine.h`; `engine/src/prefab.cpp` is new (prefab files, the diff, the sync, and the instance lifecycle that used to live in `engine.cpp`), and both scene loaders now share one `ApplyComponentEntry` so the file shape is read in one place. Serialization writes `overrides` next to `prefabPath`; `cli/lib/constants.js` is untouched (no new component type). `npm run docs:cli` regenerated `docs/cli.md`.
- **Tests:** `TestPrefabOverrides` pins that a copy matching the asset records nothing, that a tweak (colour, name, disabled component) is recorded as exactly those three keys, that editing the asset file on disk and syncing reaches the untouched copy while the tweaked one keeps its values, that an asset child move reaches both, that a deleted component and child do not come back, that a scene with no record keeps its local state, and that a plain entity reports nothing and fails a targeted sync. The CLI suite grew 187 → **202 checks** and pins the same story end to end through real processes: the record after a tweak, the reload after an external edit, `prefab.apply` reaching the sibling and rewriting the asset file (including the applied child deletion), and `prefab.revert` handing back a fresh copy of the asset subtree.

## [0.1.16] - 2026-10-17

### Physics: hinge and fixed joints
- **`HingeJoint` and `FixedJoint` join `DistanceJoint`**, so the joint family now covers what a scene actually hinges on: a door on its post, a wheel on its axle, a swinging platform (hinge), and a barrel welded to a cart or a limb to a body (fixed). Both hang off one shared primitive in `engine/src/physics.cpp`.
- **One primitive, three joints.** Everything is a *point pair*: a world point on one body driven onto a world point on the other, position then velocity, shared between the ends by inverse mass and inertia. A point offset from the centre of mass expresses rotation as well as translation, so the same code covers all three.
- **`HingeJoint` is two pairs** — the anchor, and a point one arm up the axis. Together they lock five degrees of freedom and leave rotation about the axis free; the second pair is what keeps a swing in its plane. It has `connectedGuid` / `anchor` / `connectedAnchor` / `axis` (all in the joint's local space) plus Unity's optional `useLimits` + `limitsMin`/`limitsMax` and `useMotor` + `motorVelocity` (degrees per second) / `motorForce`.
- **Limits are a hard stop about the pin.** The angle is measured from the pose the joint captures on its first step. When it passes a limit the ends are turned back about the shared anchor (not about their centres of mass), so the pin stays *exactly* satisfied the instant the step returns - and only the spin that pushed outward is cancelled, so a body resting on its limit is not locked against coming back.
- **The motor drives the joint, not the body's centre of mass.** A motorised body reaches the target rate on its first step (no spool-up) and spins *about the pin*, because the injected angular velocity is accompanied by the linear velocity that keeps the anchor still - the joint's own free rotation. `motorForce` caps the impulse per step, so a small motor lags under load rather than teleporting the load to speed.
- **The angle reads from the end that can move.** With a `connectedGuid` the angle is the connected body's rotation relative to this one (a positive motor and positive limits turn *it*), matching Unity's `HingeJoint.angle`. Anchored to the world there is nothing to turn, so the reference is this body's rest pose and the angle is this body's own swing from its captured pose (a positive motor and positive limits turn *this* body, the way the axis' right-hand rule says).
- **`FixedJoint` is a weld.** Three non-collinear point pairs (the origin, +X and +Y offsets) captured on the first step lock the whole relative pose, so B is dragged, spun and kept in step with A wherever A goes. It exposes just `connectedGuid` and `breakForce` - like Unity, a fixed joint has no usable anchor; it welds whatever relative pose it finds.
- **The point solve is exact, not iterative-by-axis.** A point pair presents a small symmetric effective-mass matrix (`invM_A + invM_B` on the diagonal minus one rank-one term per end, an isotropic inertia making the rotational response an outer product of the lever arm); `SolvePointMass` inverts it by Cramer's rule, so one pair closes in a single shot with translation and spin together. Six iterations then only need to reconcile the pairs with each other, which is why a wrench-hard weld sits still to well under a millimetre and a free swing keeps its arm length to five decimals.
- **Each pair is rebuilt from the live transforms before it is solved.** An earlier pair has already moved the bodies by the time the next one runs; solving the second against coordinates captured before that move is what made the first version fight itself (a pendulum settled 13% off its radius and drifted out of plane). Rebuilding per pair is the whole fix.
- **Breaking and waking** follow the existing joint contract: `breakForce` (0 = unbreakable) compares `(error + relativeSpeed * dt) / (inverseMassSum * dt)`, and ends are woken when that load passes a threshold. Sleeping ends stay frozen, as everywhere else in the step, so a teleported sleeping body is not yanked back until something gives it velocity.
- **Surfaces:** the component classes and their reflection tables in `engine/include/cairn/scripting.h` / `engine/src/components.cpp` (so the inspector, `component.schema` and `component.add` see them), `AddComponentByName` and the scene loader/writer, and `cli/lib/constants.js` adds `HingeJoint`/`FixedJoint` to the `component.add` enum. `npm run docs:cli` regenerated `docs/cli.md`.
- **Tests:** `TestHingeJoint` pins the free swing of a pendulum pinned to a world point (radius 1, in plane, ending straight below), a gravity-loaded door on a horizontal axis that must stay in plane and hang on its limit, an out-of-plane shove and cross-axis spin that the second pair has to take out, both limits of a pushed door, a motor at 90 degrees a second (a quarter turn in half a second and still exactly 90 deg/s in the second half) that never leaves its circle, and - separately - that a limit firing leaves the anchor exactly on its pivot. `TestFixedJoint` pins that a weld to a kinematic partner holds a crate to within 3.5 mm under gravity, drags and spins with it, does not disturb a pair already in its captured pose, and lets go when it breaks. CLI suite 177 → **187 checks** (a hand-written `.cscene` with chosen GUIDs round-trips, both joints appear in `scene.tree`, and the simulated wheel reaches its quarter turn).
- **Confirmed non-vacuous by mutation:** dropping the hinge's axis pair fails the planar/axis checks; turning the limit about the centre of mass instead of the anchor fails the pin checks; forcing the angle sign fails both door limits and the motor; giving the motor spin without the matching linear velocity fails the rate checks; and dropping the rotational coupling from the point-mass matrix fails the pendulum. ### Tooling: agent-facing drawing — see what you drew, and draw polygons
- **The image tools can now be checked without eyes.** An agent driving `cairn` cannot look at a PNG, and `image.info` only offered a 16-bin histogram plus an average color while `image.pixel` returned one pixel at a time. `image.preview` renders the document (or one `--layer`) as text: blocks of `--scale` pixels average into one cell, weighted by alpha so transparency does not wash the color out, and each cell is written as an ascii luminance ramp, a Unicode density ramp (`--format blocks`) or a single `#rrggbb` (`--format hex`). ## [0.1.13] - 2026-10-17

### Physics: continuous collision detection (CCD)
- **Fast bodies no longer tunnel through thin geometry.** The step was purely discrete: it moved a body by `velocity * dt` and only then ran the narrow phase, so anything whose single-step displacement exceeded an obstacle's thickness (a bullet, a long fall, a launched crate) ended up on the far side of it. `RigidBody` now has a `collisionDetection` field (`Discrete` | `Continuous`, Unity's `CollisionDetectionMode`); a body that opts into `Continuous` is swept before it moves and stops at the first solid static/kinematic collider in its path.
- **The sweep is a real time-of-impact, not fixed sampling.** `Continuous` bodies use conservative advancement: starting at the current position it repeatedly advances by the *current separation* from the nearest approaching obstacle, which by construction can never step past a contact. One distance function per shape pair (exact for spheres and capsules, the same AABB gap the narrow phase uses for boxes) makes it accurate as well as safe — a 0.02-thick slab stops a body moving 10 units per step, and a diagonal approach stops on the surface instead of on an inflated bounding box. Sampling-based CCD would need one sample per 0.02 units to do the same.
- **The existing solver does the response.** The displacement is clamped to just past the impact (by a small, body-relative skin), so the ordinary narrow phase still produces the contact impulse, restitution, friction and `OnCollisionEnter`/`Stay`/`Exit` events. No response code was duplicated.
- **Zero cost and zero change when unused.** The obstacle gather, the sweep and the new code path are all skipped unless a body opts in, so every existing scene runs the identical discrete step. Obstacles already in contact at the start of the step are filtered out, so a resting or sliding body is never mistaken for one about to impact.
- **Scope.** Translation only (rotation is not swept) and solid static/kinematic targets only — the same scope as Unity's `CollisionDetectionMode.Continuous`, not `ContinuousDynamic`.
- **Surfaces:** the `RigidBody::collisionDetection` enum in `engine/include/cairn/scripting.h`, the reflection table (so the inspector shows a dropdown and `cairn component.schema --type RigidBody` lists it), and scene/CLI round-trips (enum props take integers, per the existing CLI contract).
- **Tests:** `TestContinuousCollision` pins the discrete tunnel, the continuous stop (sphere, box and 2D), a wall thinner than the step, a near miss past an edge that must *not* be clipped, the diagonal stop plane, and an A/B check that a resting body slides identically with and without CCD. Confirmed non-vacuous: disabling the sweep fails 4 of the checks.

## [0.1.12] - 2026-10-17

### Performance: bindless texture arrays (batching no longer needs a shared texture)
- **The scene path samples textures through bindless arrays.** Set 1 of the scene pipeline layout is now two `sampler2D` arrays (albedo and normal, 512 slots each) instead of a per-draw albedo/normal pair. A draw stores its two slot indices in the draw uniform (`DrawUbo.texIndex`) and the fragment stage indexes the arrays, so an instanced run can span materials with *different* textures. A 60-cube scene with 6 interleaved albedo textures drops from 63 draws to 4 (one opaque run, two shadow runs, the sky pass) with a **bit-identical frame**; the software reference is unchanged.
- **`DrawUbo` gained `texIndex`** by consuming 16 bytes of the existing padding (`float pad[24]` → `float texIndex[4]; float pad[20]`), so the 256-byte stride the instancing relies on is unchanged. The shader mirrors it (`vec4 texIndex; vec4 pad[5]`).
- **One stable table, written only when it changes.** A `(texture, sampler)` pair gets a slot the first time a frame samples it and keeps it; a warm scene issues no descriptor writes at all. Slot 0 is the 1×1 white stand-in that "no texture" resolves to, so every slot in the array is a valid descriptor at all times. When the texture cache evicts a texture its slots are whited out and returned to the free list, and if every slot is live the least-recently-used one is stolen — the table degrades by slot churn, never by dropping a texture to white.
- **The sampler is part of the slot key**, so a sprite's `pixelPerfect` (clamp) and a mesh's (repeat) sampling coexist. This incidentally fixes a latent bug: the old `textureView` helper overwrote the caller's sampler with `linearRepeat`, so `pixelPerfect` sprites and bitmap text were sampled with repeat wrap — they now clamp, matching the software reference (2D scene mean difference vs software drops from 28.4 to 25.3).
- **Device features.** The backend now enables `shaderSampledImageArrayDynamicIndexing`, `descriptorIndexing` and `shaderSampledImageArrayNonUniformIndexing` (queried via `vkGetPhysicalDeviceFeatures2`, which is a new entry in the loader), and requires `maxPerStageDescriptorSampledImages >= 1024`. A device without them fails the backend with a logged reason and the software rasterizer takes over, rather than silently losing the feature.
- **Removed** the per-draw texture descriptor sets (and the placeholder set they needed); the post chain keeps its own two-sampler layout and a small pool of sets.
- **Verified** per rule 7: `VK_LAYER_KHRONOS_validation` is clean for the 3D, 2D, normal-map and texture-eviction scenes; the instanced and `CAIRN_NO_INSTANCING=1` frames are bit-identical; the GPU frame keeps tracking the software reference (identical to the 0.1.11 build for the same scenes).
- **Tests:** `TestBindlessTextureSlots` (three cubes, three albedo textures, one batched run, each third of the frame peaks in its own channel on both backends — confirmed to fail when the slot index is forced to 0).

## [0.1.9] - 2026-10-17

### Performance: job system + parallel CPU passes
- **`Jobs` (`<cairn/jobs.h>`).** One process-wide worker pool backs `Jobs::ParallelFor(count, f)`: indices are handed out dynamically, the calling thread participates, and a single `hardware_concurrency`-sized pool (capped at 16) is created lazily and shared by the whole process. The renderer's private band pool is now this shared pool.
- **Re-entrancy is handled.** A `ParallelFor` body that dispatches again would clobber the in-flight task (a single `task_` pointer into the caller's frame); a nested call is therefore downgraded to a serial loop on the calling thread instead of corrupting state.
- **`CAIRN_JOBS_WORKERS=n`** caps the pool; `n <= 1` runs everything on the calling thread, which is how the benchmark harness measures the speedup.
- **Parallelism where it is provably safe.** Work is split only where each index owns its output: the software rasterizer's row bands (as before), the whole post-processing chain (bloom bright pass + separable blur, colour grading, vignette, FXAA), and the clear/sky fill. Every parallel loop writes disjoint rows and reads only shared inputs, so the software image is **bit-identical** to the serial one; the pixel-exact suites pin this.
- **Measured.** 1280x720, 300 objects, all four post effects on: the post chain drops from 57.6 ms to 6.4 ms (≈8.9× on 16 workers) and the frame from ≈70 ms to ≈20 ms. `engine.profile` reports the per-phase split; `CAIRN_JOBS_WORKERS=1` reproduces the serial baseline.
- **Telemetry.** `Jobs::Snapshot()` (`{workers, dispatches, indices}`) is folded into `engine.profile` as `jobs`, so a host can see the pool size and how much work is going through it.
- **Docs.** Job-system and profiler sections in `docs/architecture.md`; a `Jobs::ParallelFor` example in `docs/scripting-api.md`.
- **Tests.** `TestJobs` (every index exactly once, `count <= 0` no-op, reproducible output, nested dispatch does not deadlock or clobber, telemetry advances) and a CLI check for the `jobs` block.

## [0.1.7] - 2026-10-17

### Physics: distance/spring joints and rigidbody sleeping
- **`DistanceJoint`.** Holds two bodies a fixed `distance` apart (0 = captured on the first step). `connectedGuid` names the target GameObject (empty anchors to a fixed world point at `connectedAnchor`); `anchor`/`connectedAnchor` are local offsets. With `spring` > 0 it becomes a spring/damper instead of a rigid constraint, and `breakForce` (> 0) snaps the joint once the constraint force exceeds it. Constraints are solved with a sequential (Gauss-Seidel) pass after contacts.
- **Rigidbody sleeping.** A body that stays slow for `sleepDelay` seconds (`sleepThreshold`, `allowSleep`) stops integrating and is treated as static by the solver, so resting stacks cost ~nothing. It wakes on `AddForce`/`AddImpulse`/`AddTorque`, on a non-zero `velocity`, or when a moving body touches it.
- **Bug fix: transformed AABBs no longer include the origin.** `AABB::Transformed` started from a zero-initialised box, so every transformed bound was silently unioned with the world origin — box-vs-box contacts behaved as if every box reached y = 0 until they fell through the floor, and mesh bounds used for picking/culling/shadows were inflated. It now seeds from the first corner. A `TestMath` case pins it.
- **New CLI command.** `physics.step --dt <s> --steps <n>` advances the scene physics headlessly and returns `{steps, dt, dynamic, sleeping}`.
- **Tests.** `TestJoints`, `TestSleeping` and the `AABB::Transformed` case, plus CLI checks that `physics.step` settles a falling body and that it sleeps.
- **Still to come** (next increment): per-property prefab overrides; then the rendering-performance work (instancing/batching, async GPU readback, profiler).

### Vulkan GPU rendering backend (default)
- **A real GPU rasteriser, on by default.** Frames now render through a Vulkan 1.3 backend (dynamic rendering + `synchronization2`, loaded at runtime via `dlopen`, so the engine still runs on machines with no Vulkan at all). It draws the same scene the software path does — meshes, sprites/text, debug lines, sky, cascaded shadow maps, tone mapping and the bloom/grading/vignette/FXAA post chain — and reads the result back so the host blits exactly what it always did. `RenderBackend::Auto` prefers the GPU and degrades silently to software; `RenderStats::backend` always reports what actually ran.

The host wrote the light count into the light uniform block as a `float` while `mesh.frag` reads an `int`, so one light read back as 1065353216 and the shader's light loop ran off the end of the block until the GPU faulted — any scene with a light rendered black. The texture staging buffers were freed while the copy that read them was still only recorded. Per-draw descriptor sets were rewritten while an earlier pass in the same command buffer still had them bound, which needs `UPDATE_AFTER_BIND` pools to be legal. The shadow pipeline declared `CULL_MODE` dynamic but never set it. Image layouts are now tracked per image across frames instead of guessed, the backend destructor actually releases the device, and a texture reachable twice in one frame is uploaded once instead of leaking its first image.

### PBR materials, normal mapping, texture cache (milestone 7)
- **Shared vertices in the OBJ importer.** `LoadObjFile` hashes (position, uv, normal) index triples so a corner reused across faces maps to one vertex — a 32×16 UV-sphere OBJ drops from 3072 duplicated vertices to 561 (−82%); an 8×8 grid from 256 to 81. Index sharing is what smooth shading and tangent computation both need.
- **Tangent frames.** `MeshVertex` gains `Vec4 tangent` (xyz = unit tangent orthonormal to the normal, w = bitangent handedness, w == 0 = "no frame"). `Mesh::RecomputeTangents()` builds tangents from the UV layout (Lengyel's method with a perpendicular fallback for degenerate UVs); `RecomputeNormals()` now recomputes tangents too, and `RecomputeNormalsAndTangents()` is the explicit combined entry point. All procedural generators produce valid frames, and the torus generator's normals were fixed (they mixed the ring angle into the tube term and were not unit length). The renderer transforms the tangent as a direction and carries handedness through clipping and perspective interpolation.
- **PBR-ish material response.** `MeshRenderer` gains `metallic`, `roughness` (negative = derive from shininess so pre-PBR scenes keep their look), `normalMapPath`, `normalStrength` and `emissiveColor`, all with reflection defs (inspector/CLI/`component.schema`/serialization are automatic). The Blinn-Phong lobe in `ShadeAndStore` is replaced by GGX (Smith Heitz visibility, Schlick Fresnel): dielectric F0 = `specular · 0.16`, metals take F0 from the albedo, diffuse is scaled by `(1 − metallic)` and Fresnel-weighted, the specular lobe is π-scaled to match the engine's non-physical diffuse units, and roughness maps from shininess via GGX alpha `= sqrt(2/(shininess+2))`. Emissive is added after the light loop in linear space (unlit materials stay raw albedo). Mesh normal mapping reuses the sprite axis convention (top-down v), samples the map with the material tiling, orthonormalizes the interpolated tangent against the normal and rebuilds B = `cross(N,T)·w`.
- **Per-slot texture color space.** `TextureLibrary::Get(path, srgb)` loads/caches the linear variant of a file separately from the sRGB one (the renderer requests `srgb=false` for normal maps); `setSRGB` no longer wipes an existing mip chain when the value is unchanged, and flag flips regenerate the chain. Asset `.meta` import settings will own this later.
- **Byte-budgeted texture cache.** Entries account `w·h·4·(mip chain)` bytes and evict least-recently-used above the new `textureMemoryMB` scene setting (default 256); the newest entry survives even when alone over budget. `ReloadPath` is now conditional on an mtime check and `ReloadChanged()` sweeps the cache; `Engine::ReloadAssets()` uses it instead of dropping every texture. The renderer pins each frame's referenced textures in `liveTextures` (shared_ptrs) so LRU eviction can never free a `Texture` a raw `MaterialGpu` pointer still samples.
- Tests: new native `TestMeshTangents` (unit/orthogonal/±1 handedness on every primitive), `TestObjSharing` (edge-shared quads 8→6, grid 256→81), `TestPbrMaterials` (property round-trip through serialization, metallic kills the diffuse response) and `TestTextureCache` (per-slot color space, LRU eviction under budget, mtime reload, unchanged-file no-op); CLI checks that `component.schema` lists the five new MeshRenderer props.

### Post-processing pipeline (milestone 6)
- **End-of-frame post chain** in `Renderer::RenderScene`, after the 2D pass and overlay lines, running single-threaded on the finished display-referred sRGB framebuffer: **bloom → color grading → vignette → FXAA**. Bloom does a 2×2-box bright pass with a smooth knee into a half-resolution buffer, a separable 9-tap Gaussian (horizontal into one scratch buffer, vertical back — the two scratch buffers are allocated lazily and reused across frames) and a bilinear additive composite. Grading applies contrast around the 0.5 display pivot then saturation around Rec.709 luma in one fullscreen pass. Vignette darkens radially (aspect-corrected, half-height units: strength / radius / softness). FXAA is the console-style luma-edge pass (relative + absolute luma thresholds, edge-direction estimate, two bilinear taps).
- **Color space**: the framebuffer holds tonemapped + sRGB-encoded bytes (shading is linear), so every effect operates on display-referred values; the bloom bright pass thresholds *display* luma by design (documented in the code). Exposure remains a shading-time control applied in `EncodePixel` and is not duplicated in the post chain.
- **Every effect individually switchable, and the off state is a strict passthrough**: neutral defaults (strengths 0, contrast/saturation 1.0, FXAA off) skip the chain entirely, keeping the framebuffer byte-identical to the un-post-processed render. Eight new scene settings (`postVignette`, `postVignetteRadius`, `postVignetteSoftness`, `postContrast`, `postSaturation`, `postBloomStrength`, `postBloomThreshold`, `postFxaa`) serialize into `.cscene`, flow through `CameraView`/`BuildCameraView` (clamped to their documented ranges), the addon (`scene.settings.get/set`), the CLI (`SCENE_SETTINGS`) and the inspector with labels in both languages.
- **`RenderStats::postPasses`** (0-4) counts the effects actually applied this frame; exposed through the addon.
- Tests: new native `TestPostProcessing` (passthrough determinism + byte-identical round-trip, vignette centre-untouched/corner-darker signature, bloom strictly brightens, FXAA leaves flat sky rows identical while cleaning edges, settings survive serialization) and 9 new CLI checks (settings round-trip, `postPasses` gating, unknown post setting still `invalid_arg`).

### Directional shadow mapping (milestone 5)
- **Shadows are visible and correct.** Directional-light cascade shadows now darken opaque geometry: the shadow factor was computed and counted per pixel but never applied in the 3D lighting branch (only the 2D sprite path used it), so floors looked uniformly lit.
- **Rasterizer barycentric weights fixed.** `RasterTriangle` built its edge functions as `e_i = cross(v_{i+1} − v_i, P − v_i)` (edge `v_i → v_{i+1}`) but assigned `w0 = e0`; each edge function actually belongs to the *opposite* vertex, so depth, world position, normals and UVs were interpolated with cyclically permuted weights — shadow maps stored sheared depth planes and every textured/shaded surface was subtly scrambled. Weights now map `e0 → w2, e1 → w0, e2 → w1`.
- **Cascade splits line up with the fit slices.** `ComputeCascadeSplits` no longer overwrites the first boundary with the near plane, and cascade `c` is fitted over `[splits[c−1], splits[c]]` — the same slice `SampleShadow` selects with `viewDepth <= splits[c]` (previously every pixel sampled the next cascade's map, so near geometry never found its occluders).
- **Tight cascade depth volumes.** `FitCascade` now places the light eye just in front of the nearest content and spans only the slice's light-depth extent plus fixed 1-unit world margins (previously the ortho range was ~(maxD−minD) + 4·radius + 2 ≈ 100× the geometry depth). The fit extends toward real caster bounds (laterally by up to half the slice span, in depth by up to one span) so off-slice geometry still occludes. Depth bias is authored in world units — 1.5 texels plus a 2-texel slope term at grazing light — converted by the cascade's world depth span, so it holds at any scene scale.
- **Shadow-pass culling uses the light.** The depth pass resolves polygon facing against the fitted light-space eye instead of the light node's arbitrary world position, so casters contributed only slivers of their faces to the map.
- **Conservative caster test.** `IntersectsShadowVolume` now overlaps the caster's projected corner hull with the clip cube (interval test) instead of requiring a corner inside it, so large casters that straddle a cascade (e.g. a floor) are no longer dropped.
- **Orthographic cameras get correct cascade slices** (constant cross-section instead of perspective-scaled), and cascades configured without a shadow-casting directional light stay disabled instead of sampling stale maps.
- **Primitive meshes wound outward.** `Mesh::Cube` (all 6 faces), `Mesh::Cylinder` (sides + both caps) and `Mesh::Cone` (side) were wound inward, so with back-face culling they rendered inside-out — hidden until the depth buffer became trustworthy. New native `TestMeshWinding` checks every primitive's triangle winding against its vertex normals.
- **`RenderStats::shadowedPixels` reaches the addon** (`render.editorFrame` / `render.gameFrame` / `render.screenshot`), with new CLI checks: shadows on → `shadowedPixels > 0`, `scene.settings.set --key shadows 0` → `== 0`.
- Tests: new native `TestShadows` (floor + box + sun: pixels darken measurably with shadows on, survive camera motion, and `shadowedPixels` gates on `scene.shadows`) plus `TestMeshWinding`; new CLI shadow batch. `LightComponent::shadowBias` remains reserved (still not applied — its 0.02 default as a fraction of the now-tight cascade depth would lift shadows off contact).

### Rasterization polish (milestone 4)
- **Back-face culling** with `MeshRenderer.cullMode` (Off / Back / Front, default Back) and `MeshRenderer.antialias`. Culling resolves the facing once per clipped polygon with Newell's method, so fan triangles produced by the clipper can never disagree with their polygon (this also fixes stray sliver pixels around clipped geometry).
- **Edge coverage antialiasing**: the signed distance to the nearest edge (in pixels, from the edge functions divided by edge length) becomes a coverage value; partial pixels blend with the framebuffer and skip the depth write, so edges are smooth without cracks.
- **Sorting layers**: `SpriteRenderer` and `TextRenderer` gained `sortingLayer` (coarse) next to `orderInLayer` (fine), and transparents now sort by view-space depth instead of world Z, so ordering is correct for any camera orientation. Sprites and text never cull and stay pixel-crisp when `pixelPerfect` is set.
- Tests: new native `TestCullingAndAA` (Off/Back/Front are exact complements, antialiasing produces intermediate edge pixels) and `TestSortingOrder` (2D items reach the frame, `sortingLayer` serializes).

### Color pipeline (milestone 3)
- **Linear-space shading with an sRGB display transform.** Textures carry a color space flag (`Texture::setSRGB`, on for image files and procedural color textures); albedo, material colors, ambient, light colors and fog are decoded to linear before lighting and encoded back to sRGB when written, which is what makes the lighting behave physically instead of washing out.
- **Tone mapping + exposure** as scene settings: `tonemap` (none / Reinhard / ACES / filmic, default ACES) and `exposure`, serialized in `.cscene`, exposed through the addon, `scene.settings.*`, and new inspector rows in both languages.
- **sRGB-aware mipmaps**: sRGB textures are decoded, averaged and re-encoded so mip levels do not darken.
- **The scene background now reaches the renderer** — it was serialized but the viewport camera hardcoded a clear color. The sky gradient is derived from it (darker overhead, hazy horizon) and keeps its hue.
- Tests: new native `TestTonemapping` (ACES rolls highlights off, exposure brightens, background color reaches the framebuffer, settings round-trip through serialization) and 3 new CLI checks for the display-transform settings.

### Rendering quality (milestone 2)
- **Mipmaps and trilinear filtering.** `Texture` now builds a full mip chain on load (`GenerateMipmaps`, 2x2 box filter) and samples it through `SampleLod`; the rasterizer derives a per-triangle level of detail from the ratio of texture area to screen area. Minified surfaces no longer shimmer, which was the single most visible rendering defect.
- **New wrap mode `Mirror`**, plus per-level `SampleLevel` addressing.
- **View frustum culling.** `Frustum::FromViewProj` / `Frustum::IntersectsAABB` (Gribb/Hartmann plane extraction with a positive-vertex AABB test). Meshes, sprites and text outside the view are skipped before any vertex is transformed.
- **Richer `RenderStats`**: `frustumCulled`, `drawCalls2D` and `lightCount` alongside the existing counters (exposed through the addon and `render.*` CLI commands).
- **Cached mesh bounds.** `Mesh::Bounds()` is computed once and reused; culling, picking and selection no longer walk the vertex buffer every frame.
- **Vertices are transformed once per mesh** instead of once per triangle corner (3x less transform work for shared-vertex meshes), using reusable scratch buffers instead of per-triangle heap allocations.
- **Light limit is now reported** (a warning instead of silently ignoring lights past 16).
- Tests: new native cases `TestFrustum` (accept/reject on-screen and off-screen boxes, near plane, far plane) and `TestTextureMips` (chain shape, flat-colour preservation across levels, non-power-of-two, all three wrap modes).

### Engine correctness (milestone 1)
- **World matrices can no longer go stale.** `Transform` now tracks its cached local matrix and the parent's world version, so writing `position`/`rotation`/`scale` directly (as gameplay scripts do) or moving a parent refreshes the whole subtree. This fixes the shipped 3D template, whose orbit camera never moved during play.
- **Subtree duplication fixed.** `Scene::SerializeSubtree()` / `InstantiateCopy()` added; `entity.duplicate` and `Gameplay::Instantiate` now deep-copy children (they silently dropped them before because the serializer never emitted the nested `children` array).
- **Physics runs in world space.** Shapes are built from the entity world matrix (so rotation-aware AABBs and parented bodies are correct) and dynamic bodies integrate in world space, converted back to the parent's local space. The index-coupled two-pass shape refresh was replaced with a single post-integration gather.
- **`Component::enabled` is now honoured** by the renderer (meshes, sprites, text, lights), by picking/selection and by physics (colliders and rigid bodies). Disabling a component in the inspector previously did nothing.
- **Script instances are owned by their component.** `ScriptComponent::DestroyInstance()` calls `OnDestroy` and frees the instance wherever a Script component or its GameObject leaves the scene, so runtime destroys no longer leak and always fire `OnDestroy`.
- **Hot reload during play keeps the game running**: loading a script library while playing re-runs the script startup instead of leaving every script dead.
- **Script inspector defaults are applied on load.** Fields declared by `DescribeProps` after a scene was authored now read back with their declared default instead of `0`.
- **Trigger semantics fixed.** A trigger sensor no longer turns its body's solid contacts into triggers; trigger/contact pairs are tracked per scene (no process-global state), and `OnTriggerExit` / the new `OnCollisionExit` are delivered even when a collider or entity is removed mid-play.
- **New collision callbacks**: `Component::OnCollisionEnter/OnCollisionStay/OnCollisionExit` for solid contacts.
- **Removed a framebuffer data race.** Opaque rasterization is split into row bands with one owner per band, so no two threads write the same colour or depth texel (previously up to 16 threads raced on every pixel). The job pool publishes its task atomically across epochs.
- **Blended geometry is depth tested** (without writing depth), so sprites and text are occluded by opaque geometry instead of always drawing on top.
- Tests: 3 new native cases (`TestHierarchy`, `TestParentedPhysics`, `TestTriggerAndEnabled`), 11 new smoke checks (lifecycle, hot reload during play, prop defaults, enable flags) and 3 new CLI checks (render stats, subtree duplicate).
